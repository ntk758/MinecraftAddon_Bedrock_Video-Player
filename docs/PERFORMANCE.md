# 性能の測り方と結果 / Performance

このプロジェクトの「速さ」には、まったく別の 2 つがあります。

| | 変換の速さ (PC) | 再生の性能 (Minecraft) |
|---|---|---|
| 何の速さか | 動画を `.mcaddon` にする時間 | ゲームの中でブロックを置き替える負荷 |
| 決めるもの | PC の CPU / GPU、動画の長さ、解像度、ディザ | 1 秒に置き替えるブロックの数 (解像度 × fps × 変化の割合)、端末の速さ |
| 遅いと | 待ち時間が長いだけ | ゲームが重くなる・映像が遅れる・音とずれる |
| 測り方 | `benchmark/convert_perf.py` | `/scriptevent <接頭辞>:stats` (と `:bench`) |

「変換が速い = ゲームで軽い」ではありません。GPU は変換を速くするためのもので、ゲーム内の負荷は変わりません。

## 1. 変換の速さ・メモリ (PC)

**条件** (毎回同じ): 入力は ffmpeg で作る `testsrc2` 1280×720 30 fps 30 秒 → 10 fps で 300 フレームに変換。
パレットは拡張 33 色。時間は動画の読み込みから書き出しまで全部。メモリは変換プロセス (子プロセスを含む) の最大の物理メモリ、
VRAM は Windows のパフォーマンスカウンター「GPU Process Memory」の専用メモリの最大。

```bash
python benchmark/convert_perf.py --out bench_out      # 結果: bench_out/results_convert.md
```

**結果 (2026-10-12)**: Windows 11、CPU `Genuine Intel(R) 0000` (OS の表示どおり、32 スレッド)、RAM 32 GB、
GPU AMD Radeon RX 9070 XT (DirectML)、Python 3.12.15、PyTorch 2.4.1 (+ torch-directml)、ffmpeg 9.0.1

| 設定 | デバイス | 時間 | 速さ (出力フレーム/秒) | 最大メモリ | 最大 VRAM | 出力 |
|---|---|---|---|---|---|---|
| 平面 128×72、Blue Noise | CPU | 3.8 秒 | 80 | 171 MB | — | 178 KB |
| 平面 128×72、Blue Noise | GPU (DirectML) | 8.0 秒 | 38 | 374 MB | 84 MB | 274 KB |
| 平面 256×144、Blue Noise | GPU (DirectML) | 15.3 秒 | 20 | 360 MB | 141 MB | 847 KB |
| 平面 128×72、ディザなし | CPU | 4.1 秒 | 73 | 160 MB | — | 147 KB |
| 立体 relief 64×48×16、ディザなし | CPU | 3.5 秒 | 86 | 152 MB | — | 168 KB |

- この PC では **CPU の方が GPU より速く**、データも小さくなりました。GPU 経路は OkLab での色合わせ・RDO・時間方向のディザを
  行うぶん処理が多く、条件付き更新 (`--temporal-hysteresis`) は CPU 経路にだけあるためです。GPU は解像度が大きいときや
  CPU が遅い PC で効く可能性があります (未計測)。
- 長い動画の時間は、おおむねフレーム数に比例します (例: 3 分 20 秒を 20 fps → 4000 フレームなら、上の速さで 1〜2 分)。
- 最大メモリは 2 パスのストリーミング処理なので動画の長さにほとんど依存しません。

ほかの PC の結果は、`results_convert.md` をそのままこの表の下に追記してください。

## 4. ゲーム内の性能 (Minecraft)

### 4.1 ブロックを置く費用 (`/scriptevent <接頭辞>:bench`)

スクリーンの範囲で、置き方ごとの 1 ブロックあたりの時間を測り、`auto` の描画方式がこの値を使います (ワールドに保存)。

| 日付 | 端末 | setBlockPermutation | fillBlocks (行) | fillBlocks (面) | fillBlocks (座標リスト) |
|---|---|---|---|---|---|
| 2026-10-11 | Windows 11 (作者の PC、v6.0.0、24×24 マス) | 2.31 µs | 1.16 µs | 0.58 µs | 1.45 µs |

このときの計測は合計 2〜8 ms と短いため、±10〜50% の誤差があります。ほかの端末の値を追記してください。

### 4.2 再生の fps・遅れ・音声とのずれ (`/scriptevent <接頭辞>:stats`)

再生中または再生後に実行すると、直前の再生 (最後に開始・再開してから) について次を表示します。

| 表示 | 意味 |
|---|---|
| 実効 fps | 実際に表示したフレーム数 ÷ 実時間。目標 fps を下回るなら追いついていない |
| サーバー TPS | 1 秒あたりの tick 数 (本来 20)。下がっているとゲーム全体が重い |
| 実時間とのずれ | 再生を始めてからの実時間 − 表示した映像の時間。正なら映像が遅れていて、音声 (実時間で進む) が先に進んでいる。音声は 10 秒ごとの区切りで映像の位置から鳴らし直すので、ずれはその間だけ残る |
| 遅れて描き始めたフレーム | 表示時刻が来た tick より後に描き始めたフレームの数と、最大の遅れ (tick) |
| スクリプト時間 | 1 フレームを描くのにかかったスクリプトの時間 (平均・最大、ms)。1 tick は 50 ms で、アドオンは 1 tick に約 30 ms までしか使わない |

| 日付 | 端末 / Minecraft の版 | 動画 (幅×高さ、fps、ディザ) | 実効 fps | TPS | ずれ | 遅れたフレーム | スクリプト時間 平均 / 最大 |

### 4.3 メモリ

Script API にはメモリ使用量を測る手段が無いため、ゲーム内のメモリは計測していません。目安として、アドオンが持つのは
動画データ (`.js` の文字列、出力の大きさとほぼ同じ) と、盤面 4 枚ぶん (幅 × 高さ × 奥行き × 2 バイト × 4) と、
展開済みの GOP 最大 4 個です。

## 5. 解像度・fps・圧縮と再生の負荷の関係

再生の負荷 ≒ **1 秒に置き替えるブロック数** = 幅 × 高さ × fps × (1 フレームで変わる割合) × 1 ブロックの費用

- **解像度** (幅 × 高さ): マスの数に比例して重くなる。128×72 → 256×144 で 4 倍。
- **fps**: 比例して重くなる。10 → 20 fps で 2 倍。20 fps は 1 tick ごとに 1 フレームなので、間に合わないとすぐ遅れる。
- **変わる割合**: 映像で決まる。アニメ・字幕は 4% 前後、パンや細かい模様は 7〜12%、場面の切り替えでは 100% 近く。
  ディザ (Blue Noise など) は粒が動く場面で割合を上げる。条件付き更新 (既定) は下げる。
- **圧縮** (データの大きさ): 主に `.mcaddon` の大きさと読み込みの時間に効く。再生の負荷とはほぼ無関係
  (データが小さくても、置き替えるブロックが多ければ重い)。
- **立体**: 置くのは表面と側面が中心。幅 × 高さ × (奥行きの数段ぶん) が目安。

GUI の **再生負荷の目安** は「画面全体が毎フレーム変わる最悪の場合」に 1 tick あたり何 ms 置くかを示し、
8 ms 未満を「軽い」、25 ms 未満を「普通」、それ以上を「重い」としています (1 ブロック 1.5 µs で計算)。

## 6. 初心者向けのおすすめ設定

| 目的 | 設定 |
|---|---|
| まず試す・スマートフォン | 軽量 (64×64、20 fps) か 標準 (96×96、10 fps) |
| PC でふつうに見る (既定) | 高画質 128×128、10 fps (16:9 なら「縦横比に合わせる」で 128×72) |
| 細かく見せたい | 高精細 128×128、5 fps か ウルトラ 256×256、5 fps (PC 推奨) |
| 動きの多い映像 | fps を上げるより解像度を下げる |

迷ったら既定のまま作り、再生後に `stats` を見て、遅れたフレームが多ければ 1 段軽い設定にしてください。
