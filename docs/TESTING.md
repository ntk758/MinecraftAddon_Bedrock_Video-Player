# テストの範囲と記録 / Test scope and records

このプロジェクトのテストは「自動テスト (pytest + Node、CI で毎回実行)」と「実機テスト (Minecraft で人が確かめる)」の 2 つです。
自動テストは Minecraft の API を **モック** (`tests/js/minecraft_mock`) で置き換えて動かすので、実機でしか分からないこと
(実際の速さ・描画・音・端末ごとの違い) は実機テストで確かめます。

## 1. 自動テスト (Automated)

`pytest -q` (約 20 秒) で全部を実行します。GitHub Actions ([ci.yml](../.github/workflows/ci.yml)) が `main` への push と
プルリクエストごとに、Ubuntu・Python 3.12・Node.js 20・CPU 版 PyTorch で実行します (README の CI バッジ)。

| 対象 | 何を確かめるか | テスト |
|---|---|---|
| 符号化・復元 | Python の参照デコーダと `codec.js` が全フレームで同じ盤面を作る。シークの結果が通常再生と同じ | `test_codec_v4.py`, `test_rle_roundtrip.py`, `test_motion.py`, `test_tiles.py` |
| 立体 | relief / extrude / inflate / vox、3D 動き補償、2.5D の平面 (変わった列だけの組み立てが全体の組み立てと同じ) | `test_volume.py`, `test_volume3d.py`, `test_planes.py` |
| アドオン (`main.js`) | モックの Minecraft で再生し、最後の画面のブロックが正しい。描画方式 (auto / rect / list / block) で結果が同じ。変わったブロックだけ置く。シーク・一時停止・再開・動画の切り替え・クリア・常時読み込み・建築限界・`bench`・`stats` | `test_main_js.py`, `test_render_modes.py`, `test_playback_control.py` |
| 減色 | ディザ・条件付き更新・自動パレット (色空間・色数)・GPU 経路 (CPU 版 PyTorch で同じコードを実行)・ブロックモードの最適化 (置く費用を増やす候補を選ばない、変換結果がそのまま復元できる) | `test_temporal.py`, `test_device.py`, `test_block_rdo.py` |
| GUI | 変換の引数、プリセット、縦横比の提案、設定の検査、負荷の目安、パックの UUID / バージョン | `test_gui_options.py` |
| 翻訳 | 10 言語でキーと `{}` の置き換えがそろっている。アドオンが使う翻訳キーがすべてある | `test_i18n.py`, `test_main_js.py` |
| 画質指標 | MS-SSIM (1 段では scikit-image の SSIM と一致) | `test_ms_ssim.py` |

**自動テストで分からないこと** (実機テストで確かめる):
- Minecraft の本物の API の振る舞い (モックは仕様書と実機で確かめた動きをまねているだけ)
- 再生の速さ・重さ (モックの API はほとんど時間がかからない。`bench` / `stats` を実機で使う)
- 音の再生と映像との同期
- GPU (CUDA / ROCm / DirectML) の実機での減色 (CI は CPU 版 PyTorch で同じコードを動かすだけ)
- Windows 用 EXE の起動と変換 (リリース時に手で確かめる)
- スマートフォン・ゲーム機・専用サーバーでの動作

### 2.1 だまし絵の重さを実機で測る (o40・o80・dancer)

モックの時間は、実機の約 3.1〜4.6 倍が目安 (見積り。実機の値が届くたびに直す) で、だまし絵の重さの定数 (`video_player_gui.py` の
`MMD_STAGE_MS_AT_40`・`MMD_STAGE_COST_EXPONENT`) もこの見積りから出している。実機の値は次の 3 本で測る。手元だけにある第三者の
モデルから作った試験用アドオンなので、リポジトリにも配布物にも入れない (数字だけを記録する)。

| 名前 | 中身 |
|---|---|
| o40 | MMD の人物 (高さ 40 のだまし絵)。背景の映像なし |
| o80 | 同じ人物を高さ 80 に (エクストリーム)。背景の映像なし |
| dancer | 人物を切り抜いた立体 (高さ 45 ほど) + 後ろの壁の背景の映像 |

1. アドオンを取り込み、新しいワールド (チート有効、ビヘイビアーパックとリソースパックの両方を有効) で `/scriptevent badapple:setup`。
2. 舞台の箱の中か手前に立ち、**動かずに**最後まで再生する (`/scriptevent badapple:start`)。終わったらすぐに `/scriptevent badapple:stats`。
3. もう一度、今度は舞台の前を左右に歩き回りながら (目を動かして) 最後まで再生し、同じように `stats` を見る。
4. 出た 3 行を記録する。
   - `再生` (stats_play): フレーム数・fps・TPS・映像の遅れ。目標の fps と TPS 20 に届いたか
   - `負荷` (stats_load): 予定より遅れて描き始めたフレームの数・最大の遅れ (tick)、1 フレームのスクリプト時間の平均と最大 (ms)
   - `舞台` (stats_stage): 人物を壁と床へ写した時間の平均・最大 (ms)・回数と、目の動きで描き直しを始めた回数 (だまし絵だけ)
5. 読み方: 実機の `Date.now()` は 1 ms 単位なので、`舞台` の最大は 1 ms 刻み。投影 1 回は数 ms なので、平均 (合計 ÷ 回数) で見る。
   1 フレームの平均 (`負荷`) のうち投影が占める分は「平均 × (回数 − 描き直しの回数) ÷ フレーム数」(描き直しの投影はフレームの時間の外で走る)。
   残りは展開と設置。動かずに再生したときの回数は変わるフレームの数と同じで、歩き回ると描き直しの分だけ増える。
   統計は再生している間だけ数えるので、止めた後や bench の間の描き直しは入らない。
6. 記録の形 (表の欄が足りなければ [PERFORMANCE.md](PERFORMANCE.md) に表を足す):

| 名前 | 目の動き | fps / 目標 | TPS | 遅れ (最大 tick) | 1 フレーム 平均 / 最大 ms | 投影 平均 / 最大 ms (回数) | 描き直し | モックの 1 フレーム ms |
|---|---|---|---|---|---|---|---|---|
| o40 | 動かない |  |  |  |  |  |  |  |
| o40 | 歩き回る |  |  |  |  |  |  |  |
| o80 | 動かない |  |  |  |  |  |  |  |
| o80 | 歩き回る |  |  |  |  |  |  |  |
| dancer | 動かない |  |  |  |  |  |  |  |
| dancer | 歩き回る |  |  |  |  |  |  |  |

「モックの 1 フレーム ms」は `python benchmark/stage_bench.py --addon <アドオン>` の `stats_load` の平均 (同じアドオンを実機の費用をまねた
モックで再生した値)。実機 ÷ モックが、見積りの 3.1〜4.6 倍に収まるかを見る。収まらなければ見積りの倍率を、`MMD_STAGE_MS_AT_40` などの定数は
実機の値が届いてから、別の変更で直す。

#### 前後の比較 (v6.28.0 と、この版)

この版には、ゲーム内の FPS・TPS・フレーム時間を v6.28.0 と比べた記録が **まだ無い** (数値はモックの通し再生と、そこからの見積り)。
次の手順で、同じ条件の前後の比較を取る。

1. o40・o80・dancer の 3 本を、v6.28.0 のコードのアドオンと、この版のアドオンの両方で用意する。
   変換データは同じで、アドオンの JS (`main.js` と `codec.js`) だけが違うようにする。切り抜きの安定化で人物のマスクは変わるので、
   **切り抜きの dancer は同じ変換結果 (同じマスク) を両方に使う**。
2. 同じワールド・同じ場所・同じ舞台の位置で、上の手順 (動かない・歩き回る) を 1 本ずつ、版を交互に 3 回ずつ行い、`stats_play` `stats_load` `stats_stage` の中央値を記録する。
   版による差と、回ごとの差 (同じ版どうし) を並べて見る。同じ版どうしの差より大きい変化だけを効果とみなす。
3. 見る列は、fps / 目標、TPS、遅れたフレームの数と最大の遅れ、1 フレームの平均・最大 ms、投影の平均 ms。
   v6.28.0 には `stats_stage` の行が無いので、投影の時間は比べられない (1 フレームの平均から見積もる)。
4. 結果は [PERFORMANCE.md](PERFORMANCE.md) に表で足し、モックの値 (`python benchmark/stage_bench.py --baseline <v6.28.0 の木>`) との比を出す。
   実機 ÷ モックが 3.1〜4.6 倍に収まらなければ、見積りの倍率 (`benchmark/stage_bench.py` の `GAME_RATIO`) を直す。
   (v6.28.0 のころの実機の値とモックの比は、o40 で約 4.4、o80 で約 4.6 だった。)

### 2.2 人物の切り抜き (AI) の記録

GUI は人物の切り抜きを別のプロセスで行い、処理ログには結果の短いまとめを 1〜2 行だけ出す (人物が空のフレームが 10% を超える・予備の
モデルが 50% を超える・目立つ物の切り抜き (BiRefNet) を外した、のどれかなら注意の 1 行を足す)。くわしい記録は次のファイルに残る。

- `%LOCALAPPDATA%\BlockVideoPlayer\logs\person-YYYYMMDD-HHMMSS.log`: 子プロセスの出力すべて (やり直した段階の分も続けて) と、統計の JSON の行。
  新しい 10 個だけ残る。失敗のダイアログにもこのファイルの場所が出る
- `person-stats-YYYYMMDD-HHMMSS.json`: 同じフォルダに子プロセスが書く統計。windowed の EXE のように標準出力を読めなくても残る

**ログには入力の動画の場所 (ユーザー名を含むことがある) が書かれる**。人に送るときは確かめてから。統計の JSON は、成功したときは場所を含まないが、失敗したとき (`error.message`) は動画の場所が入ることがある。

統計の JSON (`python scripts/make_person_videos.py ... [--stats PATH]` の `stats {...}` の行も同じ):

| 項目 | 中身 |
|---|---|
| `model` `profile` `profile_reason` `profile_skipped` | 使った切り抜きのモデルと段階、その段階にした理由 (`auto` = 空きメモリから、`given` = 指定、`retry_memory` `retry_crash` = 前の段階がメモリ不足・落ちたため、`retry_model` = アニメ向けのモデルを取得できず photo の段階へ進んだため)、より重い段階にしなかった理由 |
| `free_at_start` | 始めたときの空きの RAM と VRAM (MB。分からなければ `null`)。GUI が最初に測った値をやり直しの段階にもそのまま渡すので、やり直しの段階ではその段階の開始時の値ではない |
| `sources` `flagged` | 出所ごとのフレーム数 (`anime` そのまま / `filled` 前後で埋めた / `matched` 合わせた予備 / `fallback` そのままの予備 / `rejected` 面積の上限 (0.6) か位置の検査で採らずに空にした予備。写真向けだけのときは `photo`)。`flagged` はアニメ向けが人物を見つけなかったフレームの数 |
| `fallback` | `reasons` 予備に頼った理由 (`long_run` 見つけない連なりが 3 枚以上 / `no_neighbour` 場面や動画の端 / `no_fallback`)、`model` `why` 予備に何を選んだか (`salient` `photo` `none`) とその理由、`frames` 予備が返した数 (モデル別)、`load_s` |
| `salient_dropped` | BiRefNet を外したフレームと理由 (`oom` メモリ不足 / `slow` 遅くなった / `error` 実行中の失敗)。外していなければ `null` |
| `empty_frames` `scene_cuts` | 書き出したマスクの人物が画面の 0.5% 未満のフレームの数、場面の切り替わりの数 |
| `models` | モデルごと (`anime` `photo` `salient`) の実行プロバイダー (`providers`。onnxruntime の `get_providers()`) と、推論の ms (`ms`: `n` `mean` `median` `p95` `max`)。Windows では `peak_mb` `peak_ws_mb` (モデルを作る前から最初の推論の後までに、プロセスの最大の commit・working set が増えた MB。プロセス単位の最大値の増え分なので下限の目安) |
| `stages_ms` | 工程 (`read` `segment` `split` `write`) ごとの、1 回の呼び出しの ms (`n` `mean` `median` `p95` `max`) と合計 `total_s` |
| `load_s` `run_s` `wall_s` | モデルを作る・フレームを処理する・全体の秒数 |
| `memory` | このプロセスの最大の working set と最大の commit (MB。Windows のみ、他は `null`) |
| `error` | 失敗したときの理由 (`kind`: `input` `model` `out_of_memory` `crash` と `message`)。成功なら `null` |

空きメモリの安全閾値は環境変数で上書きできる: `BVP_PROFILE_NEEDS_GB` (段階ごとに要る空きの RAM:VRAM を GiB で。例 `full=12:12,gpu=2:1`)、`BVP_MIN_FREE_RAM_MB` (処理中に要る空きの RAM を MB で)。不正な値は無視して既定値を使う。

ローカルの `benchmark/person_bench.py` は、この統計を行に入れ、マスクの動画から数えた空のフレームの数・場面の切り替わりの数と合っているかを
`stats_check` に出す。

### 2.3 人物の切り抜き: 音声と映像の長さが違う動画 (実際の AI のモデル)

`tests/test_person_audio_length.py` は、**偽の切り抜き** (常に空のマスクを返す関数) で、背景の動画の書き出し (ffmpeg) だけを確かめる。
次の手順は、**実際の AI のモデル** (写真向けの DeepLabV3 と、アニメ向けの anime-seg) で、切り抜きから書き出しまでを通して確かめるもの。
結果は、下の表の「結果」の欄に書く。行っていない行は「未実施」のままにして、完了扱いにしない。

**試験用の動画の作り方** (人物が映っている自作の動画 `person.mp4` を 1 本用意する。第三者の動画は使わない):

```
ffmpeg -i person.mp4 -t 8 -an base.mp4
ffmpeg -i base.mp4 -f lavfi -i "sine=f=440:d=2" -map 0:v -map 1:a -c:v copy -c:a aac short_audio.mp4
ffmpeg -i base.mp4 -f lavfi -i "sine=f=440:d=20" -map 0:v -map 1:a -c:v copy -c:a aac long_audio.mp4
ffmpeg -i person.mp4 -t 0.6 -c:v libx264 -c:a aac sub_second.mp4
ffmpeg -i person.mp4 -t 30 -c:v libx264 -c:a aac normal.mp4
```

- `long_audio.mp4` は、映像 8 秒・音声 20 秒 (コンテナの長さは 20 秒になる)。
- 音声なしは `base.mp4` を使う。

**実行** (Python の環境。EXE では `--run-person-split` で同じ引数):

```
python scripts/make_person_videos.py <入力> mask.mp4 background.mp4 --fps 10 --model photo --stats .
python scripts/make_person_videos.py <入力> mask.mp4 background.mp4 --fps 10 --model anime --stats .
ffprobe -v error -count_frames -show_entries stream=codec_type,duration,nb_read_frames -of csv=p=0 mask.mp4 background.mp4
```

**見るもの:**
- 終了コードが 0 で、`input error` の行が出ない。
- 人物の範囲と背景の動画のフレーム数が同じで、元の映像の長さ × 10 fps に等しい。
- 背景の動画の音声の長さが、映像の長さ ± 0.05 秒 (音声なしの入力では、音声のストリームが無い)。
- 作業フォルダに `*.video-only.mp4`・`*.muxing.mp4` が残っていない。
- 切り抜きの品質: 1 秒・中ほど・最後のコマで、人物の範囲が直す前の版 (v6.37.1) と同じ。同じ入力・同じモデルで比べる。音声の長さの修正は、切り抜きの計算を変えていない。
- GUI で同じ動画をだまし絵にすると、後ろの壁の映像が最後まで流れ、音声が途中で切れない。

| 入力 | 写真向け (photo) | アニメ向け (anime) | GUI のだまし絵 | 日付・環境 |
|---|---|---|---|---|
| 音声が映像より短い (`short_audio.mp4`) | 成功 | 成功 | パックは成功・ゲーム内は未実施 | 下 |
| 音声が映像より長い (`long_audio.mp4`) | 成功 | 成功 | パックは成功・ゲーム内は未実施 | 下 |

## 5. 画像モード (方式 A / C) を実機で確かめる

試作の画像モード (docs/IMAGE_MODE.md) を、方式 A と C それぞれについて確かめる手順です。結果は方式ごとに「4. リリースごとの記録」の備考に書きます。

### 準備
1. 自作か合成の映像で変換する (例: `ffmpeg -f lavfi -i testsrc2=s=640x360:r=30:d=10 -f lavfi -i sine=d=10 -shortest test10.mp4`)。数字が毎コマ変わる `testsrc2` は、コマの飛びと音ズレが見やすい。
   `python convert_image_mode.py test10.mp4 --width 64 --height 36 --fps 30 --method both -o test10_image.mcaddon`
2. 取り込んで、新しいワールド (クリエイティブ、昼、平地) でビヘイビアーパックとリソースパックを両方有効にする。前に同じ名前で作ったパックが入っていれば先に外す (版番号が変わらないため、古いものが使われることがある)。
3. 開いた直後に設定 → 「コンテンツ ログ」を有効にし、エラーが出ないことを確かめる。

### 方式ごとに行う (`/bvpimg:setup test10` の後、`/bvpimg:method a` と `/bvpimg:method c`)
1. **表示崩れ**: `/bvpimg:start`。画面全体が出るか (欠け・左右反転・上下逆・裏向き)、マスの境目に隣のコマの線がにじまないか、夜 (`/time set night`) に暗くならないかを見る。斜めと遠く (画面の幅の 2〜4 倍) からも見る。
2. **fps**: 画面を 60 fps で録画し、10 秒の間に絵が変わった回数を数える (testsrc2 は左上のコマ番号で数えられる)。300 回なら 30 fps、200 回前後なら 20 fps に落ちている (q.life_time が tick 刻みのとき)。F3 相当が無いので、端末の fps はゲームの設定の「fps を表示」で見る。
3. **音ズレ**: 録画で、testsrc2 の秒の表示と音のチャンクの頭 (4 秒ごと) を比べ、ずれを 0.1 秒単位で書く。`pause` → 3 秒待つ → `resume` の後、次の 4 秒の境目まで無音になり、その後ずれないことを見る。
4. **チャンクの読み直し**: 再生中に画面から 200 ブロック以上離れ (飛行)、5 秒後に戻る。戻ったとき、正しい位置のコマ (録画の時刻から計算) に 1 秒以内で戻るかを見る。離れている間に `/bvpimg:pause` してから戻った場合も見る (止まっているべき)。
5. **ワールドの開き直し**: 再生中に保存して終了し、開き直す。チャットに「再生を戻しました」が出て、閉じたときの続きから進むかを見る。
6. **重さ**: 画面を見たまま `/bvpimg:method a` と `c` を切り替え、端末の fps の差を書く。

記録すること: 端末、Minecraft の版、方式、見えたコマ数/10 秒、音ズレ (秒)、読み直し後に戻るまでの秒数、fps の差、崩れの有無。
