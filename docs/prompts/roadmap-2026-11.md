## 依頼文 (ここから下を貼る)

このリポジトリ (Block & Image Video Player) に、README の「🧭 今後の機能の構想 (2026-11 の案)」の機能を順に実装してほしい。作業の前に必ず次を読むこと: `README.md` のその節、`TODO.md` (特に「進め方の決まり」と「スクリーンシステムの次の段階」)、`ARCHITECTURE.md`、`DECISIONS.md`、`docs/SCREEN_SYSTEM.md`、`docs/TESTING.md`、`PROJECT_STATUS.md`。

### 守ること

1. **TODO.md の「進め方の決まり」に従う。** 既定の出力は変えない (新しい処理は任意の設定として入れる)。データ形式は足すだけで、古いアドオンでも新しい変換データが動くようにする。壊す変更は先に DECISIONS.md に理由を書く。
2. **ベータ API・実験的機能は使わない。** manifest の `@minecraft/server` 2.6.0 / `@minecraft/server-ui` 2.0.0 の範囲で作る (Realms で試験的な機能を有効にできないため)。それより新しい API が要るときは、使う前に止まって私に聞く。
3. **「実装した」と「確かめた」を分ける。** 私は実機 (Windows 11) で確かめる役。モックや自動テストで通っただけのものを「確認済み」と書かない。PR の説明に、私が実機で確かめる手順 (コマンド・見るべき点) を箇条書きで付ける。
4. **推測で API の仕様を書かない。** Script API・コマンド・Minecraft の仕様は Microsoft Learn (learn.microsoft.com/minecraft/creator) などの一次情報で確かめ、PR の説明に出典を書く。確かめられないときはそう書く。
5. 変えた部分には自動テストを足す (既存の `tests/` の書き方に合わせる。JS は `tests/js/`、モックは既存のものを使う)。`pytest` と既存の JS のテストが全部通ってから PR にする。README・CHANGELOG・TODO・PROJECT_STATUS の記述もそろえる (`tests/test_docs_consistency.py` が通ること)。
6. 10 言語の文言 (`locales/*.json`) は、足したキーを全言語にそろえる。
7. ブラウザ版 (`web/`) の画面を変えるときは `.claude/skills/premium-vanilla-ui` の決まりに従う。
8. 1 つの PR に複数の機能を混ぜない。ブランチは `feature/<機能名>`。

### 手順

**0. 計画を TODO.md に移す (最初の PR)**
- README の構想の表を、TODO.md の優先度 (P1〜P3) と状態 (`未着手` など) に移す。段階 A は P1、B と C は P2、D は P3 を目安に、既存の項目 (P2-3・P3-2・スクリーンシステムの Phase 3〜5) と重なるものはまとめる。
- スクリーンシステムの **Phase 5「URL からの取り込み」は見送り** に書き換える (YouTube の利用規約がダウンロードを禁じているため。代わりに手元のファイルのドラッグ＆ドロップと区間の切り出しを楽にする)。
- TODO.md の P0 が残っている間は、新しい機能より P0 を先にやること。P0 が残っていたら、まずそれを私に報告して、どちらを先にするか聞く。

**1. ライブの計測だけ先に (段階 D のライブの可否を決める)**
- `research/` か `benchmark/` に、WebSocket サーバーになる小さな Python の計測ツールを作る。ゲームから `/connect localhost:<ポート>` で入ってもらい、`fill` / `setblock` のコマンドを一定の数ずつ送り、ゲームから返る応答で「1 秒に何本処理されたか」「応答が返らず捨てられたものはあるか」「同時に送れる未応答の数の上限」を測る。
- 送る中身は、32×18・64×36・128×72 の画面を毎フレーム塗り直す場合と、変わったところだけ送る場合 (差分) の両方。
- 結果から、使える解像度と fps の見込みを `docs/research/` にまとめる。私が実機で計測を実行するので、手順 (Windows のループバックの許可、設定の「暗号化された WebSocket を要求」を切る方法、チートの有効化) を書く。**ライブ本体はこの結果を私が見てから作る。**

**2. 段階 A (すぐ遊べる)**
- 劇場キット: 暗い部屋・スクリーンの台・座席の `.mcstructure` を作る仕組み (パックに入れる方法と、`/structure load` か Script API で置く方法を一次情報で確かめてから選ぶ)。
- 端末ごとの推奨: `stats` の計測結果から、その端末で無理のない幅・高さ・fps を出す。画像モードは TODO の P2-3 とまとめて設計する。
- 遠いスクリーンを止める: 近くに誰もいないスクリーンは描画を止め、戻ったら今の再生位置から描き直す (再生の時計は止めない)。距離は設定できるようにする。

**3. 段階 B (作る人向け)**
- スクリーンをコマンドで操作: `/<接頭辞>:screen <番号> <play|pause|stop|seek|select|loop> [引数]`。今の `screenUi.act` を使い、コマンドブロックから動くこと (権限の扱いを確かめる)。マップ作りの人向けの説明を README に足す。
- プレイリスト・字幕 (`.srt` → actionbar)・サイネージ (画像のスライドショー) の順に。

**4. 段階 C (見せる)**
- プレビューの動画の書き出し: 既存の `scripts/make_demo_video.py` の復元を、Windows 版の画面とブラウザ版から使えるようにし、縦 9:16 と任意のクレジットを足す。
- 撮影用のカメラ (`/camera`)、音のビジュアライザ (変換ツールで先に計算して普通の動画として作る)、1 コマを `.mcstructure` に、パレットの追加 (サバイバルで手に入るものだけ・光るもの中心)。

**5. 段階 D (他に無いもの)**
- 分岐する動画 (段階 B のコマンドの上に作る)、複数人の同期 (スクリーンシステムの Phase 3)、ビデオウォール、ライブ (1 の結果が良かったときだけ)。
