# 画像モードの「ガラスケースの立体」設計 (2026-11-18)

参考動画「マップアートで3Dミク動かしてみた」(Java 版) と同じ見え方を、画像モードで作るための設計です。
土台は PR #145 (`feat/image-impostor`、角度で絵を切り替える立体の試作) です。

**実装の状況 (2026-11-18)**: 5 章と 9 章を `feat/glass-case` に実装しました (`image_mode/planes.py`・`glass.py`・`glass_rp.py`、`convert_image_mode.py` のオプション、`scripts/make_planes_test_pack.py`、`tests/test_image_planes.py`)。6 章の 1〜8 は済み。4 (実機の試験) は PC で 5.8 の 1・2・5 を確かめ、板の UV の向きを決めました (DECISIONS.md の A19)。5.8 の 3・4・6・7 (陰の見え方・遠くからの見え方・重さ・2 人) はまだです。設計から変えた所は、その場所に「実装では」と書きました。

書き方: **実測** は手元のスクリプトで出した値 (ゲームの外。変換ツールと同じ `.vox` の読み込みと `image_mode/impostor.py` の `dense_frames` を使用)、**見込み** は計算や推測。実機の Minecraft で確かめた結果は、5.8 と DECISIONS.md の A19 にあります。

## 1. 作りたい見え方

参考動画では、マップアートでできた箱の中にフィギュアが立って踊っています。歩いて回り込んでも上から覗いても立体に見えます。箱の奥の面には背景の絵があり、手前の面は透けて向こうの景色が見えます。

画像モードで目指すこと:

| | 目標 |
|---|---|
| G1 | どの向きから見ても立体に見える (水平 360 度、上から、斜め下から) |
| G2 | 歩くと見え方が連続して変わる (PR #145 のように 45 度ごとに絵が跳ばない) |
| G3 | マルチプレイで、見ている人それぞれに正しく見える |
| G4 | ケース (水槽) がある: 床 (台座)・奥の壁の背景の絵。手前の壁は透けて景色が見える |
| G5 | 立体アニメ (`.vox`) を繰り返し再生できる (PR #145 と同じ) |

目標にしないこと: 普通の動画 (2D) から、回り込める立体を作ること (奥行きと裏側の情報が無い)。MMD などのなめらかなモデルを直接読むこと (7 章)。
普通の動画は、奥の壁で流すか、前から見る浮き彫りにして使います (9 章)。

## 2. 参考の仕組み

投稿者の説明を要約すると、次の 3 つです。

1. 水槽の中のフィギュアが見えるのは、フィギュアからの光がガラスを通って目に届くから。ガラスの面から同じ光を出せば、中に何も無くてもフィギュアがあるように見える。
2. 正しく見えるのは 1 つの目の位置からだけなので、プレイヤーの視点に合わせて計算し直し、マップアートの表示を更新し続ける。
3. 透けている所は、透明な額縁とエンドの奈落を組み合わせた既知の手法。

1 と 2 は、コンピューターグラフィックスでいう「head-coupled perspective (fish tank VR)」です。目の位置 E から立体の点 P へ向かう線が箱の面と交わる所に、P の色を描きます。

```
   目 E
    \
     \        箱の面 (スクリーン)
      \       |
       \      |
        ●-----|------→  P (フィギュアの点。実際には無い)
       描く点 |
```

このプロジェクトのブロックモードには、同じ方式がもうあります (`--view anamorphic`、v6.20.0)。床と 3 枚の壁の箱に、見ている人の目の位置から見たとおりにブロックで人物を描き、歩くと描き直します。

## 3. 画像モードでそのまま真似できない理由と、代わりに使えるもの

| | 参考 (Java のマップアート) | 統合版の画像モード |
|---|---|---|
| 絵を描き直す | サーバーが計算して、マップの画素を送り直す | 絵はリソースパックの PNG だけ。`@minecraft/server` にテクスチャやマップの画素を書く API はありません。描き直しはできず、用意した絵から選ぶことしかできない |
| 目の位置 | サーバーがプレイヤーの位置を読む | スクリプトも読めるが、それで絵を選ぶとエンティティのプロパティに書くことになり、全員に同じ値が届く (1 人分にしか合わない)。クライアントの Molang なら、見ている人ごとに自分のカメラとの角度と距離を毎フレーム読める (`q.rotation_to_camera(0)` 上下・`(1)` 左右、`q.distance_from_camera`) |
| 透明 | 透明な額縁 + 透明の画素 | アルファテストのマテリアル (`entity_alphatest`) |
| 立体 | 箱の面に「投影した絵」を描く | エンティティは、厚みの無い板を空間の好きな位置に、好きな向きで置ける。板に貼った絵は、ゲームの GPU が見ている人ごとに毎フレーム遠近を付けて描く |

ここから、この設計の考え方が出てきます。

> 投影を自分で計算しない。立体そのものを板で作ってケースの中に置き、投影はゲームの GPU に任せる。

参考がガラスの面に投影しているのは、Java のマップアートが「ブロックの面に貼った額縁」にしか置けないからです。統合版のエンティティなら、板を立体の中に直接置けます。そうすれば G1〜G3 は GPU が満たします。見ている人ごとに、毎フレーム、サーバーとの往復なしに描くからです。

## 4. 比べた案

数は、`scripts/make_demo_dancer.py` の踊る人物を高さ 128 ボクセル (73×46×128)・40 コマで作って出しました。

| 案 | しくみ | テクスチャ (40 コマ、RGBA) **実測** | 見え方 | 判断 |
|---|---|---|---|---|
| P 投影 | 参考どおり、箱の面ごとに「目の位置の見本」から見た投影を前もって描き、Molang で一番近い見本を選ぶ | 測っていない。見本の数 × 面の数 × コマなので、I より多い | 見本の間で跳ぶ。面の境目で絵がずれる | 不採用 |
| I 角度の絵 (PR #145 を広げる) | 立体を何方向かから描いた絵を、カメラへ向けた板に映す | 8 方向 13.8 MiB。上下 3 段 × 16 方向 = 48 方向で 82.5 MiB | 境目で跳ぶ (48 方向でも 22.5 度ごと)。板の中に奥行きが無い | 軽さが要るときの予備 |
| S 中心の断面 | ボクセルの層 (中心を通る断面) を板にして 3 方向に重ね、見る向きに近い束を見せる | 51.7 MiB | 斜めから見ると細い所が痩せる。隙間が見える画素が高さ 128 で最大 8% (45 度で 6.1%)、高さ 56 で最大 17% | 不採用 |
| **F 面の板 (推奨)** | ボクセルの「外に出ている面」を、軸ごとの平面にまとめて板にする (5 章) | **31.5 MiB** | 本物の立方体と同じ (下の確かめ) | **採用** |
| V 立方体 | ボクセルをそのまま geometry の立方体にする | テクスチャは小さい | 本物と同じ | 1 コマ 12,553 面 (まとめる前) で geometry が重い。F の分け方 `tile` (5.3) がこの間にあたる |

F が本物と同じに見えることの確かめ (**実測**): 光線を 1 本ずつ飛ばして、「本物のボクセルの立方体」と「F の板」で最初に当たるボクセルを比べました。正射影、1 ボクセル 2 画素、1 コマ目。

| 見る向き | 高さ 56 | 高さ 128 |
|---|---|---|
| 正面 (0.3 度) | 穴 0・違うボクセル 0 | 穴 0・違うボクセル 0 |
| 横に 22.5 度・45 度 | 同上 | 同上 |
| 斜め上 (45 度、上へ 35.26 度) | 同上 | 同上 |
| 上から 60 度 | 同上 | 同上 |
| 後ろの斜め下 (200 度、下へ 40 度) | 同上 | 同上 |

同じ方法で S (中心の断面) を測ると、45 度で穴 6.1%・違うボクセル 46% (高さ 128) でした。

## 5. 推奨の作り: 面の板

### 5.1 しくみ

立体の大きさを (sx, sy, sz) ボクセルとします。x の軸には、ボクセルの境目 x = 0, 1, …, sx に sx + 1 枚の板を置きます。y と z も同じです。

- 板 x = k の画素 (y, z) は、ボクセル (k-1, y, z) と (k, y, z) の**片方だけ**が埋まっているときに色を持ちます。色は埋まっている方のボクセルの色です。両方とも空、または両方とも埋まっているときは透明です。
- つまり板 x = k は、その平面にある「外に出ている面」を全部集めたものです。3 軸の板を合わせると、ボクセルの表面がちょうど全部そろいます。
- `entity_alphatest` は板の両面を描きます (PR #145 の実機で確認済み)。表面の裏側は必ずそのボクセルの内側にあり、手前の別の面に隠れるので、両面を描いても結果は変わりません。アルファテストは深さを書くので、板の並べ替えも要りません。
- 板は全部いつも見せます。Molang でカメラの向きを計算する必要も、どの板を見せるか選ぶ必要もありません。PR #145 で苦労した符号 (DECISIONS.md A18) の問題も出ません。

```
横から見た図 (x の板だけ。■ はボクセル)

  x=0   1   2   3
   |  ■ | ■ |   |      x=0 の板: 左のボクセルの左の面
   |  ■ | ■ | ■ |      x=1 の板: 内側どうしなので透明
   |    | ■ | ■ |      x=3 の板: 右の面
```

面の明るさは、PR #145 と同じくブロックの面の割合 (上 1.0・下 0.5・東西 0.6・南北 0.8) を色に焼き込みます。ゲームのエンティティの陰と二重にならないかは、実機で比べます (5.8)。

### 5.2 大きさ (**実測**、踊る人物・40 コマ)

| | 高さ 56 (32×20×56) | 高さ 128 (73×46×128) |
|---|---|---|
| 外に出ている面 (1 コマ) | 2,310 | 12,553 |
| コマごとに板を切り詰める (`rect`): 板 / コマ | 81 | 193 |
| 同: テクスチャ (40 コマ) | 2.6 MiB | 31.5 MiB |
| 同: geometry の板の合計 | 3,237 | 7,715 |
| 8×8 の区画に分ける (`tile8`): 板 / コマ | 380 | 1,998 |
| 同: テクスチャ (40 コマ) | 3.7 MiB | 19.5 MiB |
| 正面から見たときの重なり (`rect` / `tile8`) | 15.6 倍 / 17.3 倍 | 36.6 倍 / 18.5 倍 |
| 参考: 全コマ共通の配置にした場合 | 4.5 MiB | 53.9 MiB |

「重なり」は、正面から見たとき、人物が写る 1 画素あたりに何枚の板 (透明な所を含む) が重なるかです。透明な所もアルファテストで捨てるまでは GPU の仕事になります。

### 5.3 重さの調整

板 1 枚を大きな長方形のままにすると、板は少ないが透明な所が多くなります (`rect`)。区画に分けると、板は増えるが透明な所が減ります (`tile8`)。高さ 128 なら `tile8` で重なりが半分、テクスチャも約 6 割になります。

どちらが軽いかは端末で変わるので、オプション `--plane-split rect|tile8|tile16` にして実機で fps を比べてから既定を決めます。**見込み**: PC はどちらでも問題なし。スマートフォンは重なり 36 倍が効く可能性があります。

### 5.4 コマ (アニメーション)

- コマごとに板の位置と大きさが違うので、geometry はコマごとにボーン `f<n>` を持ち、その中にそのコマの板を入れます。render controller は `part_visibility` で `v.frame == n` のボーンだけを見せます。
- テクスチャは、1 枚のシートに決まった数 K のコマを詰めます。`v.sheet = math.floor(v.frame / K)` で `Array.sheets[v.sheet]` を選びます。シートの中の位置は geometry の UV に直接書くので、方式 a の「マス」の格子は使いません。
- 時計とコマの同期 (`seq`・`frame`・`pre_animation`) と繰り返し (`loop`) は、PR #145 をそのまま使います。
- コマ数には上限を設けます (最初は 240 コマ。高さ 128 で板およそ 4.6 万枚)。これを超えるときは、全コマ共通の配置 (5.2 の最後の行) に切り替える案を後で作ります。
- テクスチャの量は、今の `atlas.memory_report` (Tier 2 の 225 MB で警告、Tier 5 の 800 MB でエラー) でそのまま調べます。

### 5.5 ケース (水槽)

参考の「奥の面には背景、手前の面は透明」は、内側だけを向いた板で再現できます。

```
上から見た図

        奥の壁 (内向き) → 表が見える: 背景の絵
     +-----------------+
     |                 |
左の壁|      人物       |右の壁
     |                 |
     +-----------------+
        手前の壁 (内向き) → 裏しか見えない: 描かれず透明

            目
```

- 壁は片面だけを描くマテリアルにします。手前の壁は裏から見ることになるので描かれず、奥の壁だけが背景として見えます。回り込むと、どの壁が「奥」になるかが自動で入れ替わります。
- 実装では: マテリアルが裏を描くかどうかに頼らず、下の予備 (Molang で隠す) を最初から使います。どちらでも同じに見えます。
- PR #145 までの記録では、不透明の `entity` が裏を描かないことは実機で未確認です (SPEC.md)。描いてしまう場合の予備: カメラがどの壁の外側にいるかを Molang で求め (`q.rotation_to_camera(0)`・`(1)` と `q.distance_from_camera` から、体の向きを引いてケースの中での位置にする)、その壁を `part_visibility` で隠します。
- 部品: 床 (台座)、4 枚の壁、天井 (付けるかは選べる)、縁 (細い枠)。絵は `--case-image back=bg.png` のように壁ごとに渡すか、1 枚を全部の壁に使います。
- 1 つの render controller では、ボーンごとに別のテクスチャを選べません。人物のシートはコマで切り替わるので、ケースは別の render controller・geometry・テクスチャにして、client_entity の `render_controllers` に人物と並べます。
- 奥の壁で普通の動画を流す作りは 9.1。

### 5.6 置き方とスクリプト

- `/bvpimg:setup <ID>` は、見ているブロックの上の床にケースを置き、こちらを向けます。`face` (東西南北にそろえる) と `align` (格子にそろえる) は今までどおり使えます。`wall` は使えません。
- `visible_bounds` はケース全体を含む大きさにします (小さいと、根元が画面の外に出たときに人物が消える)。
- スクリプトがすることは、コマの同期と繰り返しだけです (PR #145 と同じ)。見ている人ごとの処理は全部クライアントの GPU がするので、人数が増えてもサーバーの仕事は増えません。

### 5.8 実機で確かめること (試験用のパック)

A18 と同じく、いくつかの作り方を並べた試験用のパックを作り、数字と印で確かめます。

1. 軸の対応と UV の向き。厚み 0 の直方体の east・up・north の面に貼った絵が、正しい位置と左右で見えるか (up の面は UV の向きが違うことがある)。
2. 両面を描いたとき、表からも裏からも、ケースの中に入っても正しく見えるか。
3. 明るさ。焼き込みありとなしを並べ、エンティティの陰と二重にならないか。
4. 遠くから見たとき、縮小で細い所が欠けないか (アルファテストとミップマップ)。
5. `entity` が裏の面を描かないか (5.5 の壁)。
6. 重さ。PC とスマートフォンで `rect` と `tile8` の fps、ワールドを開くときの読み込み時間。
7. 2 人で別の角度から見て、それぞれに正しく見えるか。

実装では (2026-11-18、Windows 11・Minecraft v26.65): 1 は 16 通りのうち v5 (`FaceMapping(1, -1, 1, -1)`) だけが正しく、既定にしました。2 は前・横・後ろ・斜め上とケースの中から、立方体がつながって見えました。5 は Molang で隠す作りにしたので、`entity` が裏を描くかには頼りません (正面・西・東・後ろの外から、手前の壁だけが消えた)。3・4・6・7 はまだです。

## 6. 進め方

1. PR #145 を今の main に合わせる。今は `convert_image_mode.py` と `CHANGELOG.md` でぶつかっている。`_write_output` は `pack_builder.write_file_atomic` を使うようにする。
2. `planes.py` と、光線で比べるテスト。ゲームの外だけで、本物と同じに見えることを確かめる。
3. リソースパックと変換ツール (人物だけ。ケースなし) と、そのテスト。
4. 試験用のパックで 5.8 を確かめ、DECISIONS.md の A19 に書く。ここで `rect` と `tile8` の既定、明るさの焼き込み、`views` を残すかを決める。
5. ケース (床・壁・絵) と、setup の床への置き方。
6. 奥の壁で動画を流す (9.1)。
7. 動画の浮き彫りをケースに入れる (9.2)。先に大きさを測ってから決める。
8. 説明書き (`docs/IMAGE_MODE.md`・README)。Windows 版とブラウザ版の画面に出すのは、その後。

## 7. 限界と危ないところ

- 入力は `.vox` だけです。参考のようななめらかなモデル (MMD など) は、先にボクセルにする必要があります (この設計には含めない)。見た目はボクセルの角ばった形になります。1 ボクセル 1 画素なので、高さ 128 なら 6 ブロックの人物で 1 ブロック約 21 画素です。
- テクスチャは「表面の広さ × コマ数」で増えます。高さ 128 で 1 コマ約 0.8 MiB (`rect`) なので、200 コマで約 157 MiB です (**見込み**。Tier 1 の 150 MB を超える)。
- 光の向きは立体に固定です (ブロックと同じ)。ケースの中の明るさは、置いた場所の明るさに従います (**見込み**)。
- 透明な所は「あり・なし」の 2 段だけです (アルファテスト)。縁はぼかせません。ガラスの映り込みや色は付けません (半透明のマテリアルは並べ替えの問題があるので、後で試す)。
- 音声はありません (PR #145 と同じ)。
- 実機で確かめたのは PC の 5.8 の 1・2・5 だけです。6 (重さ) は、結果によって `rect` と `tile8` の既定やコマ数の上限を変える必要があります。

## 8. 参考との違い

- 同じ: ケースの中にフィギュアが立って見える。回り込んでも上から見ても立体。手前の面は透けて、奥の面に背景が見える。
- こちらの方が良い所: 板を GPU が描くので、見ている人それぞれに正しく、遅れも無い。斜め下を含むどの向きからでも、本物の立方体と同じ形に見える (4 章の確かめ。真下はケースの床に隠れる)。サーバーは見ている人の数に関係なく、コマの同期しかしない。
- 参考の方が良い所: なめらかなモデルと、縁の細かさ。こちらはボクセルの形と、前もって作ったコマの分のテクスチャに縛られる。

## 9. 自分の動画を使う

普通の動画 (2D) には奥行きも裏側も無いので、5 章の人物にはできません。使い方は次の 2 つです。

### 9.1 奥の壁で動画を流す

ケースの奥の壁を、今の画像モードのスクリーンにします。手前では `.vox` の人物が踊ります。

- **1 つのエンティティにまとめる**: 今の `image_main.js` は、同時に 1 つの動画 (`state.videoId`) しか再生しません。そこで「人物 + 壁の動画」を 1 つの動画の項目にして、1 つのエンティティに render controller を 2 つ持たせます。
  - 人物の render controller は 5.4 のとおりです。
  - 壁の render controller は、今の方式 a (シート・マス・`part_visibility`) をそのまま使います。
- **時計**: スクリプトが書くのは今までどおり `frame` と `seq` の 1 組です。クライアントは同じ時刻から 2 つのコマを出します。
  - 壁: 動画の fps で進め、最後で止める (今の動作)。
  - 人物: 自分の fps で進め、`math.mod` でコマ数の中を回る (繰り返し)。
- **音声**: 壁の動画の音声チャンクを、今の仕組みで鳴らします。人物の繰り返しは音声と関係なく回ります。
- **壁の向き**: スクリーンの板は north の面だけに絵を貼るので、内側へ向けて置きます。手前に来たときに消えるかどうかは、5.5 と同じく `entity` が裏を描かないかで決まります (5.8 の 5)。描いてしまう場合は、5.5 の予備 (Molang で隠す) を使います。
- **テクスチャ**: 人物と動画の合計を `atlas.memory_report` で調べます。たとえば高さ 128・40 コマの人物 (31.5 MiB) に、今の既定の動画を足した量です。
- **変換ツール**: `convert_image_mode.py dancer.vox --case-video in.mp4` のように渡します。動画側のオプション (`--fps`・`--width` など) は今と同じです。

### 9.2 動画を浮き彫りにして、ケースに入れる

ブロックモードには、動画を立体にする関数がもうあります (`mvcodec/volume.py` の `lift_frame` / `VolumeLifter`)。

| モード | 奥行き | 要るもの |
|---|---|---|
| `relief` | 明るいほど手前。`scripts/make_depth_video.py` の深度動画 (Depth Anything V2 Small) を渡すと、人物などが実際に手前へ出る | 深度動画 (なくても動く) |
| `extrude` / `inflate` | 人物の形を押し出す / 丸くふくらませる | 人物の切り抜き (`--mask-video`) |

これで作ったコマごとの立体 (パレットの番号の 3 次元配列) を、5 章の面の板にそのまま渡せます。`.vox` を読む代わりに、この立体を `planes.py` に入れるだけです。

見え方 (**見込み**):

- 正面から斜め 45 度くらいまでは、手前へ飛び出して立体に見えます。
- 横から見ると、奥行き (`--depth`、ブロックモードの既定 16) の分の厚みしかありません。
- 後ろから見ると、平らな裏か、側面の段差しか見えません。ケースの奥の壁を不透明にして、後ろへ回り込めないように置くのが向いています。
- 参考の動画のように、回り込んでも人物が立って見えることはありません。

大きさ (実装の後に **実測**。参考動画を 128×72・奥行き 16・10 fps で 10 秒 = 100 コマ):

| | `rect` | `tile8` |
|---|---|---|
| 板 / コマ | 126 | 1,900 |
| テクスチャ / コマ | 約 0.56 MiB | 約 0.39 MiB |
| 100 コマの板の合計 | 12,578 | 189,927 (警告) |

決めたこと: 既定は `rect`、コマ数の上限は 240 のまま (240 コマで約 134 MiB。Tier 1 の 150 MB 以内)。`tile8` は板が多すぎるので、長い浮き彫りには使わない。

設計のときの見込み (残しておく):

- 正面の面は、どのコマでも画面の大きさ (たとえば 128×72) の分あります。それが奥行きの段ごとの板に分かれます。
- `rect` では板 1 枚がほぼ画面全体の大きさになり、テクスチャと重なりが大きくなりそうです。`tile8` が前提になりそうです。
- 動画は `.vox` のアニメより長くなりやすいです (10 fps・30 秒で 300 コマ)。5.4 のコマ数の上限 (最初は 240) を超えます。
- 6 章の 7 では、128×72・奥行き 16 の動画で、1 コマのテクスチャ・板の数・重なりを 5.2 と同じ方法で先に測ります。そのうえで、上限を上げるか、全コマ共通の配置にするか、解像度を下げるかを決めます。

その他:

- 動画の長さを繰り返さず最後で止め、9.1 と同じく音声チャンクを鳴らします (`loop` を false にする)。
- `lift_frame` はパレットの番号を受け取るので、色は一度パレットに減色します。画像モードはブロックの色に縛られないので、動画から作ったパレットを使えます (実装では 120 色。mvcodec.volume の空気が 127 番なので、それより少なく)。ボクセルの色は 1 個 1 色です。
