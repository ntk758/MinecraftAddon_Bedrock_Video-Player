# Research & Results: Phase 7.x — Next-Gen Prediction and 3D Holograms

Phase 7.x (`varint_rle_v5`) で実装した「動き補償・タイル辞書・3D ホログラム再生」について、調べた先行事例、選んだ設計とその理由、計測結果、Phase 8 への提言をまとめます。

---

## 1. 結論

- **データ量**: v5.4.0 (`varint_rle_v4`) と同じ入力・同じ設定で、平面 128×72 は **47〜88% 減** (ディザなし)、256×144 も 54〜88% 減。効果の大きい順に「動き補償」「ラン位置の間隔符号化」「タイル辞書」。
- **描画コスト**: 同じ色の変化を箱 (`fillBlocks(BlockVolume)`) にまとめる `rect` で API 呼び出しが 1/1.7〜1/7、色ごとの座標リスト (`ListBlockVolume`) の `list` では 1 フレーム 2〜33 回 (v5.4.0 は 1 ブロック 1 回で 500〜1400 回)。
- **3D**: 立体専用の 3D 動き補償 (8×8×8 ブリック) で、動く物体の差分フレームが 2D の動き補償より 79〜87% 小さく、3D の箱でまとめた設置で押し出し立体の呼び出しが 1868 → 67 回/フレーム。
- **未計測**: ゲーム内での 1 回あたりの費用 (fillBlocks と setBlockPermutation の 1 ブロックあたりの時間など) は公開された比較が見つからず、モックでは測れません。`/scriptevent <接頭辞>:bench` を実機で走らせて決める必要があります (Phase 8.1)。

## 2. 先行事例 (Minecraft の動画プレイヤー・ホログラム)

約 20 件の類似プロジェクトを調べました。ブロックを置く方式のプレイヤーの多くは、本プロジェクトの v5.4.0 と同じく「変わった画素ごとに 1 ブロック」を書きます。置く回数を減らしている例は、次の 5 つの工夫のどれかを使っていました。

| 工夫 | 例 | このリポジトリでの扱い |
|---|---|---|
| 同じ色の行を 1 回の `/fill` にまとめる | [typhrenn/minecraft-video-generator](https://github.com/typhrenn/minecraft-video-generator)、[chiseled bookshelf 版](https://github.com/zadeviggers/bad-apple-minecraft-bookshelves) | **採用**: `rect` 描画 (横 → 縦 → 奥行きへ伸ばした箱) |
| 差分を構造物にして 1 回で置く (構造物の空白 = 変えない) | [purplesyringa の 512×384 Bad Apple](https://purplesyringa.moe/blog/we-built-the-best-bad-apple-in-minecraft/)、[minecraft-movie-player](https://github.com/AntarEspadas/minecraft-movie-player) | `bench` で `structureManager.place` を計測。採否は実機の結果しだい (Phase 8.6) |
| 1 ブロックに複数画素 (ブロックの状態・テクスチャ) | purplesyringa の 2×2 / 4×4 スプライト | 今回は対象外 (カスタムブロックとテクスチャが必要) |
| ブロックを置かず、テキスト表示・地図・UI で描く | [watermelon1024](https://github.com/watermelon1024/minecraft-video-player)、[JSON-UI-Bedrock-Videos](https://github.com/LukasPAH/JSON-UI-Bedrock-Videos) | 対象外 (メモリが 15〜24 GB 以上必要な例もある) |
| 3D: 立体を 1 体のエンティティのモデルにする | [Structura](https://github.com/RavinMaddHatter/Structura)、[HoloPrint](https://github.com/SuperLlama88888/holoprint) | Phase 8 の候補 (ブロックで置く方式とは別の表示モード) |

- Java 版の計測 (purplesyringa) では、費用は「ブロック 1 個の更新」と「変更があった 16×16×16 区画の再描画」が中心でした。API 呼び出しを減らすとスクリプトの負担が減り、変わるブロック・触る区画を減らすとエンジンとクライアントの負担が減ります。今回は両方を減らしています (呼び出し: 箱・リスト、ブロック数: キーフレームで置き直さない・relief のヒステリシス)。
- 統合版の Script API で動画をブロック再生する公開プロジェクトは、本プロジェクト以外に見つかりませんでした。

### 使った API (安定版 `@minecraft/server` 1.19.0 で確認)
- `Dimension.fillBlocks(volume, block)`: `BlockVolume` (直方体) と `ListBlockVolume` (任意の座標の集まり) の両方を受け付ける (1.16.0 以降)。
- `world.structureManager` (`createEmpty` / `place` など): `bench` で使用。
- `Dimension.cloneBlocks` は 2.10.0 (Minecraft 26.50) からで、1.19.0 には無いため今回は使っていません。
- `tickingarea` は 1 区画 100 チャンクまで。v5.4.0 は 256×144 以上のスクリーンで登録に失敗して設置できなかったため、10×10 チャンクずつに分けました。

## 3. コーデックの先行事例と採否

| 先行事例 | 内容 | 採否 |
|---|---|---|
| Autodesk FLIC (FLI/FLC) の DELTA チャンク | 位置を「前の続きからのスキップ」で書く | **採用**: ランの位置を直前のランの終わりからの距離に (−27〜43%、下の表の「差分のみ」列) |
| GIF の LZW / LZ78 | 符号化側と復号側が同じ規則で辞書を作り、辞書は送らない。Clear コードで初期化 | **採用**: 暗黙のタイル辞書 (キーフレームで初期化) |
| HEVC スクリーンコンテンツ符号化 (IBC・パレットモード) | 文字・図形で −10〜31%、アニメ・カメラ映像ではほぼ 0% | 期待値の目安。合成映像でもアニメ風・図形で効き、自然な映像ではほぼ効かなかった |
| Smacker / RoQ / Cinepak | 4×4〜8×8 のブロックごとに SKIP・単色・2 色マスク・コードブック・動きを選ぶ | Phase 8.5 (ブロックモードの最適化) |
| Bad Apple の移植 (NES / C64 / Game Boy / Mega Drive / espbadapple) | 変わった行のビットマップ、シーンごとのタイル量子化、LZ4、反転一致の辞書 | 非可逆のタイル量子化は文字が崩れるため不採用。LZ・エントロピー符号は Phase 8.4 |

調査段階のシミュレーション (合成映像) では、可逆のタイル辞書単独の効果は −1〜15% にとどまり、ラン位置の間隔符号化 (−29〜49%) の方が大きい結果でした。そこで両方を実装し、エンコーダがフレームごとに小さい方を選ぶ形にしています。タイルの大きさは内容で最適値が変わる (シルエットは 4×4、アニメ風は 8×8) ため、`--tile-size auto` で両方を符号化して小さい方を残します (動き探索の結果は共有)。

## 4. 実装した設計と理由

### 4.1 フレームごとの方式の選択 (`mvcodec/stream.py`)
差分のみ / 動き補償 / タイル参照 / 両方 の 4 通りを実際に符号化して、一番小さいバイト列を採用します。推定ではなく実測で選ぶので、新しい道具を足してもデータが大きくなることはありません。

### 4.2 論理盤面と表示盤面の分離 (`main.js`)
- 予測に使う「直前のフレーム」(`decoded`) と、ワールドに実際に置かれているブロック (`board`) を別に持ちます。
- これでキーフレームでも全ブロックを置き直す必要がなくなり、置くのに失敗したマスは「不明 (-1)」にして次のフレームで置き直せます。自動パレットで GOP が変わったときだけ表示中の盤面を「不明」にします。
- 計測: アニメ風 128×72 で置くブロック数 513 → 365 / フレーム。

### 4.3 3D 動き補償
立体を (奥行き×高さ) 行の 2D 画像として 2D の動き補償にかけると、奥へ・手前へ動く物体は予測できません (奥行き方向のずれが「行のずれ」として飛び飛びになるため)。8×8×8 のブリックごとに (dx, dy, dz) を ±2 から探す 3D の動き補償にしました。±2 なら 125 通りで、ベクトル 1 本が varint 1 バイトに収まります。

### 4.4 立体の生成
- **relief のヒステリシス**: 前フレームの段から連続値が 1 段未満しか動いていない画素は段を変えません。量子化の境目で揺れる画素がなくなり、置き直すブロックが減ります。
- **元の明るさを使う**: 奥行きと立体にする範囲は、減色・ディザ前の元の映像の明るさから決めます。ブロック色の明るさを使うと、ディザの粒がそのまま奥行きのノイズになるためです (この変更でヒステリシスの効果が −2% → −11〜34% に)。
- **inflate**: 4 近傍の距離変換 (収縮の繰り返し、numpy のみ) で縁からの距離 d を求め、厚みの半分を `sqrt(d × D / 2)` にします (Teddy のシルエットのふくらませ方を単純化したもの)。
- **中空化を既定で無効に**: 箱でまとめて置く場合、詰まっている立体の方が箱が大きく、呼び出しもデータも少なくなります (押し出し: 中空化すると呼び出し 67 → 184、データ +46%)。

### 4.5 MagicaVoxel の読み込み
- vox の x → 東、y → 北 (大きいほど奥)、z → 上 と「回転」で対応させます (以前の対応は行列式 −1 の鏡像で、すべてのモデルが左右反転していました)。
- 0.99 以降のシーングラフ (nTRN / nGRP / nSHP / LAYR) とアニメーションのキーフレームを [ogt_vox](https://github.com/jpaver/opengametools) と同じ規則で評価し、RGBA チャンクが無いファイルには仕様の既定パレットを使います。

## 5. 計測

### 方法
- `benchmark/codec_bench.py`: 合成映像 5 種 (パン・アニメ風・白黒シルエット・ffmpeg の `testsrc2` / `mandelbrot`、各 60 フレーム、10 fps、39 色) を、比べる版 (既定 `main` = v5.4.0) と作業中の版の `convert.py` で変換し、出力 `.js` の大きさと deflate 圧縮後の大きさ、モックの Minecraft で `main.js` を再生したときの 1 フレームあたりの API 呼び出し数・置いたブロック数を数えます。
- 立体は `--suite volume` で、3D 動き補償を入れる前の版 (`96e1f14`: 2D 動き補償・中空化・奥行きの段ごとの長方形) と比べます。

```bash
python benchmark/codec_bench.py --out bench_out --sizes 128x72 256x144
python benchmark/codec_bench.py --out bench_out --suite volume
```

## 6. 採用しなかった案

| 案 | 理由 |
|---|---|
| 非可逆のタイル量子化 (シーンごとのコードブック、Bad Apple 64 / Cinepak 型) | シルエットで −26〜68% と大きいが、2〜4.5% の画素が変わり、字幕が崩れる。実際に変わるより 2.8 倍多くブロックを書く |
| 画面から構造物を作って辞書のタイルを置く (`createFromWorld` → `place`) | 1 つの構造物が平均 1.1〜1.6 回しか再利用されず、実機でも `structure.place` は 1 ブロック 2.31 µs (座標リストの 1.6 倍) で見送り (13 章) |
| タイルの 8 通りの回転・反転 | 調査では −3〜9% (動き補償なし)。Phase 8.5 で見積もり直し、Blue Noise では 0〜4.6% (上限) でデータ形式の変更に見合わず見送り (12 章) |
| `cloneBlocks` で動きベクトルのブロックをコピー | Phase 8.6 で見積もり、コピーが 1 ブロック 0.5 µs でも描画時間 −1% 以下で見送り (13 章) |
| エンティティのモデルで立体を表示 (HoloPrint 型) | ブロックで置く方式とは別の表示方式になり、リソースパックの生成が大きく変わる。Phase 8 以降の候補 |

## 7. Phase 8 への提言

| 項目 | 根拠 |
|---|---|
| 8.1 描画方式の自動選択 | `list` は呼び出しが `rect` の 1/10〜1/300 だが、1 回あたりの費用 (座標リストを作る費用・1 ブロックあたりの費用) は実機でしか分からない。`bench` の結果をワールドに保存して使う |
| 8.2 ディザの時間的安定化 | Blue Noise ではパンの削減率が −88% → −43% に落ちる。前フレームと同じ番号で色差が許容内なら変えない、ディザ模様を全体の動きに合わせてずらす |
| 8.3 2.5D パラメトリック立体 | relief / extrude / inflate は「色 + 高さ」の 2 枚の 2D 映像で表せる。2D の動き補償・タイル辞書がそのまま効き、調査では relief で約 −69% |
| 8.4 エントロピー符号化 | xz で v5 のデータがさらに 22〜39% 縮む。ハフマン (Smacker 型) か LZ4 型なら JS でも軽く復号できる |
| 8.5 ブロックモードの最適化 | 8×8 ごとに SKIP / 動き / 単色 / 2 色マスク / 辞書 / ラン を、データ + 呼び出しの費用 + 色差 で選ぶ。調査ではアニメ風で呼び出し −29〜47% |
| 8.6 構造物とクローン | 構造物の 1 回の設置・`cloneBlocks` の 1 回のコピーで、置く回数をさらに減らす (API の移行が必要) |
| 8.7 ホログラムの素材と入力 | ステンドグラス・発光ブロックの半透明パレット、AI 深度推定の深度動画、16 ブロック区画にそろえた設置 (再描画される区画を減らす) |
| 8.8 実映像での評価 | 合成映像は辞書の再利用を多く (または少なく) 見積もるおそれがある。公開できる実映像のデータセットと、ゲーム内の tick 時間の計測を CI に |

## 8. 実機での計測 (2026-10, Windows 版)

`/scriptevent badapple:bench` (24×24 = 576 ブロック、各 6 回、スクリプト側の時間):

| 方式 | µs/ブロック | 1 回あたりの呼び出し |
|---|---|---|
| setBlockPermutation | 2.31 | 576 |
| fillBlocks (1 行ずつ) | 1.16 | 24 |
| fillBlocks (全面 1 回) | 0.58 | 1 |
| fillBlocks (ListBlockVolume) | 1.45 | 1 |
| structure.place | 2.31 | 1 |
| runCommand(fill) | 2.03 | 24 |

1 行ずつと全面 1 回の差から、`fillBlocks` は **1 回 約 15 µs + 1 ブロック 約 0.55 µs**、`setBlockPermutation` は 1 ブロック約 2.3 µs、座標リストは 1 ブロック約 1.4 µs と分かりました。モックで数えた回数に当てはめると、細かい絵 (パン) では rect 約 6.6 ms・list 約 1.5 ms・block 約 2.4 ms、押し出し立体では rect 約 3.4 ms・list 約 6.4 ms・block 約 10 ms で、**最適な方式はフレームの内容で変わります**。これを受けて描画方式 `auto` (8.1) を実装しました。構造物 (`structure.place`) と `fill` コマンドは速くないため、8.6 の優先度を下げます。Date.now は 1 ms 単位で合計 2〜8 ms の測定なので値は目安です (bench は回数を増やし、1 回の費用と 1 ブロックの費用を分けて求めるよう改良しました)。

## 9. Phase 8.2: ディザの時間的安定化

Blue Noise (GUI の既定) は模様が画面に固定されているので、カメラがパンすると模様の上を映像が流れ、パレット番号の変化が多くなる。2 つの方法を実装して比べた (128×72、60 フレーム、合成映像)。

**A. ディザ模様を映像の全体の動きに合わせてずらす** (`mvcodec/dither_motion.py`、`--dither-follow-motion`): 連続するフレームの全体のずれを推定し (縮小画像で粗く → 元の大きさで ±縮小率を細かく、1 フレーム 3〜4 ms)、その累積だけ周期的な Blue Noise / Bayer 模様をずらす。GPU 経路では前フレームの誤差・番号も同じだけずらす。

| 映像 | データ | 1 フレームで変わる画素 |
|---|---|---|
| パン (Blue Noise) | 221 → 70 KB (−68%) | 10.2% → **46.2%** |
| アニメ風 (Blue Noise) | +18% | 2.9% → 27.8% |
| シルエット (Blue Noise) | +20% | 5.7% → 18.9% |

パンでは「前のフレームをずらしたもの」になるのでデータは大きく減るが、模様が中身と一緒に動くため **画素の値は毎フレーム変わり、ゲーム内で置くブロックは 4.5 倍** になった。人物などの動きを全体の動きと取り違える映像では、データも増えた。ゲーム内の負荷は置くブロック数でほぼ決まる (実機で 1 ブロック 1.4〜2.3 µs) ので、**既定では無効** にした。

**B. 条件付き更新** (`--temporal-hysteresis`、既定 24): 前のフレームのパレット番号の色が、新しく選んだ色より RGB の距離で 24 以内しか悪くならない画素は前の番号のままにする。誤差は毎フレームの元の色と比べるので、ずれは積み重ならない。GPU の減色には同様の仕組み (RDO) がもともと入っているので、CPU の減色に追加した。v6.2.0 との比較 (データ / 置くブロック / 3×3 でぼかした色の平均誤差):

| 映像 | ディザ | データ | 置くブロック/フレーム | 誤差 |
|---|---|---|---|---|
| パン | Blue Noise | −48% | 949 → 470 (−51%) | 16.8 → 19.5 |
| mandelbrot | Blue Noise | −25% | 578 → 424 (−27%) | 46.1 → 49.5 |
| シルエット | Blue Noise | −21% | 523 → 485 (−7%) | 25.9 → 24.9 |
| testsrc2 | Blue Noise | −19% | 1038 → 900 (−13%) | 75.3 → 75.7 |
| アニメ風 | Blue Noise | −7% | 266 → 218 (−18%) | 34.8 → 35.4 |
| パン | なし | **+55%** (27 → 43 KB) | 918 → 543 (−41%) | 21.6 → 22.2 |

ディザなしのパンだけデータが増えるのは、純粋な平行移動は動き補償で完全に予測できたのに、色を変えない画素が残ると予測が外れるため (relief の奥行きのヒステリシスと同じ)。置くブロックはどの映像でも減るので既定で有効にした。

## 10. Phase 8.3: 2.5D パラメトリック立体

relief / extrude / inflate の立体は、どの列も「1 色で連続した 1 区間」なので、色の平面と値の平面 (relief は表面の段、extrude / inflate は中央にそろえた段数) の 2 枚で正確に表せる。2 枚を縦に重ねた (2H)×W の 2D 映像として平面スクリーンと同じ符号化をし、アドオンで変わった列だけ立体に組み立て直す (`mvcodec/planes.py`、`codec.js` の `expandPlanes`)。

64×48×16、60 フレーム、ボクセルのまま送る場合 (`--volume-encoding voxels`) との比較 (`python benchmark/codec_bench.py --suite volume`):

| 映像 / モード | データ (.js) | deflate 後 | 呼び出し/フレーム rect / list | ブロック/フレーム | スクリプト時間/フレーム (モック) |
|---|---|---|---|---|---|
| シルエット / extrude | 170 → 15.3 KB (−91%) | 54.8 → 8.5 KB (**−85%**) | 67 / 2.4 (同じ) | 4424 (同じ) | 1.7 → 1.1 ms |
| シルエット / inflate | 156 → 32.1 KB (−79%) | 77.0 → 17.9 KB (**−77%**) | 743 / 2.3 (同じ) | 4522 (同じ) | 1.9 → 1.5 ms |
| mandelbrot / relief | 164 → 73.9 KB (−55%) | 92.5 → 42.5 KB (**−54%**) | 387 / 21 (同じ) | 1472 (同じ) | 1.2 → 1.1 ms |
| testsrc2 / relief | 25.1 → 11.0 KB (−56%) | 10.7 → 4.7 KB (**−56%**) | 21 / 3.3 (同じ) | 903 (同じ) | 0.8 → 0.8 ms |

- 置く立体はボクセルで送った場合とマス単位で同じ (テストで確認) なので、呼び出し・置くブロックは変わらない。
- 省略するフレームの判定を平面の変化率で行うと、立体より多く省略してしまった (testsrc2 で 24 → 41 フレーム)。組み立てた立体で測るようにして、同じ判定にそろえた。
- 調査時の見積もり (relief で約 −69%) より relief の削減が小さいのは、ボクセルの方もヒステリシスと 3D 動き補償で既に小さくなっていたため。シルエット系は側面・奥行き方向の情報が 1 つの値にまとまるので大きく減る。
- 平面の動き補償は色と値を同じベクトルで予測するので、奥行きだけが変わる動き (物体が手前に来る) には効かない。値の平面に「全体に +k」の予測を加えるのは今後の候補。

## 11. Phase 8.4: GOP ごとのエントロピー符号化

**下調べ** (`benchmark/entropy_study.py`): v5 のバイト列 (payload) を、GOP ごとにバイト単位の静的ハフマン符号にすると −22〜−42%、意味ごとのストリームに分けると −28〜−54%、xz (強い LZ) で −38〜−59%。ストリームに分けたハフマンは xz に近く、JS でも表を引くだけで復号できるので採用した。
エントロピー符号の出力はほぼランダムなので、`.mcaddon` の deflate では縮まず、15bit の文字を UTF-8 にした 3 バイトのぶんが残る (乱数のバイト列を 15bit 文字にして deflate すると 1.21 倍)。今の v5 は deflate が 15bit 文字のむだをほぼ取り戻していて、`.mcaddon` の大きさは payload とほぼ同じ。そのため `.mcaddon` の削減は payload の削減より小さくなる。

**結果** (`benchmark/codec_bench.py`、128×72・60 フレーム・自動パレット、v6.5.2 との比較。入れ物を開いた中身は v6.5.2 とバイト単位で同じで、置くブロックも同じ):

| 映像 | ディザ | .js (ゲーム内のメモリ) | .mcaddon (deflate) |
|---|---|---|---|
| パン | なし | 50.4 → 25.2 KB (**−50%**) | 26.4 → 17.0 KB (−36%) |
| パン | Blue Noise | 129.3 → 60.9 KB (**−53%**) | 65.3 → 41.5 KB (−36%) |
| アニメ風 | なし | 16.8 → 10.9 KB (−35%) | 8.9 → 6.5 KB (−26%) |
| アニメ風 | Blue Noise | 57.0 → 33.0 KB (−42%) | 27.9 → 18.4 KB (−34%) |
| 白黒シルエット | なし | 17.6 → 11.2 KB (−36%) | 9.8 → 7.2 KB (−27%) |
| 白黒シルエット | Blue Noise | 39.3 → 23.1 KB (−41%) | 21.8 → 15.3 KB (−30%) |
| testsrc2 | なし | 51.4 → 33.0 KB (−36%) | 31.3 → 23.0 KB (−26%) |
| testsrc2 | Blue Noise | 83.0 → 52.8 KB (−36%) | 51.6 → 37.2 KB (−28%) |
| mandelbrot | なし | 101.0 → 58.9 KB (−42%) | 58.1 → 39.6 KB (−32%) |
| mandelbrot | Blue Noise | 105.2 → 61.7 KB (−41%) | 59.8 → 40.9 KB (−32%) |

立体 (64×48×16、2.5D): .js −30〜−41%、.mcaddon −23〜−32% (シルエット / extrude 16.8 → 11.2 KB、inflate 33.7 → 20.8 KB、mandelbrot / relief 76.0 → 44.8 KB、testsrc2 / relief 10.6 → 7.5 KB)。

**復号の時間** (QuickJS の WebAssembly 版 quickjs-emscripten で計測。ゲームの QuickJS はネイティブなのでこれより速いと考えられる): 一番大きい GOP の例 (256×144・Blue Noise・60 フレーム、v5 で 330 KB) で、文字列 → バイト列が v5 の 56 ms → 28 ms (文字列が短くなるため)、入れ物を開くのに 104 ms (ハフマンの復号 50 ms・v5 のバイト列の組み立て 54 ms)。最初の実装 (1 バイトごとに関数を呼ぶ、記号の表が 2 つ) は 351 ms だった。展開は yield の間の 1 回の処理が最大 8 ms になるよう区切っている (組み立ては出力 32 KB ごと)。
GOP の展開は、先読み (`runJob`) でも再生のジェネレータの中でも少しずつ行い、1 tick の時間の予算 (30 ms) で区切る。以前は再生の開始・シークで GOP を一度に展開していた (v5 でも最大 300 フレームの GOP で 0.4 秒ほど止まりうる) ので、v6 にしたことでかえって引っかかりが無くなった。展開の yield を 1 tick の yield の回数の上限 (ブロック数の上限) に数えると、展開に何十 tick もかかるので数えない (テストで確認)。

## 12. Phase 8.5: ブロックモードのレート歪み最適化

**方式** (`mvcodec/block_rdo.py`、`--block-rdo`、既定の強さ 16): 減色したフレームを 8×8 に分け、ブロックごとに 6 つの候補から「色の誤差 + 強さ × (ゲーム内で置く費用 + データ量)」が一番小さいものを選ぶ (Smacker・RoQ 型のモード選択)。
- 候補: 減色のまま (表示中の色が十分近いマスは表示中のまま = 条件付き更新) / 前のフレームのまま / 動き補償の予測 / 1 色 (元の平均色に一番近いブロック) / 1 色 (一番多い番号) / ブロック内で多い 2 色だけ。
- 色の誤差: OkLab の二乗誤差。3×3 でぼかした画像どうしの差に、画素ごとの差を 0.1 倍で足す。ぼかすのは、ディザの粒を「平均の色」として評価するため (画素ごとの差だけだと単色の方が良く見える)。
- 費用: 置く時間はアドオンの費用のモデル (Windows 版の実測。箱 15 µs + 1 ブロック 0.55 µs か、座標リスト 1 ブロック 1.42 µs の安い方)。データはランの数 × 1.5 バイトを 1 バイト 2 µs に換算し、動き補償した予測との差で数える。どれも 8×8 の中だけで数える近似。
- 減色のままより費用が減らない候補と、置く時間が増える候補は選ばない。最初の版はこの制約が無く、ぼかした誤差だけ小さい候補を選んで置くブロックとデータがかえって増えた。パンでは、動き補償の予測を選ぶとデータは大きく減るが、条件付き更新で残せたマスまで置き直して置くブロックが 6〜11% 増えた。
- 選んだ結果は普通のフレームとして符号化するので、データ形式とアドオンは変わらない (v6.6.0 のアドオンでもそのまま再生できる)。平面スクリーンだけに使う (2.5D の立体の色の平面には v6.10 で対応。16 章)。

**結果** (`benchmark/rdo_bench.py`、128×72・60 フレーム・自動パレット、強さ 0 との比較。呼び出しは rect 方式、描画時間は rect と list の見積もりの小さい方):

| 映像 | ディザ | ΔE2000 | MS-SSIM | データ (deflate 後) | 呼び出し | 置くブロック | 描画時間 |
|---|---|---|---|---|---|---|---|
| パン | なし | 11.33 → 10.68 | 0.804 → 0.788 | 34.7 → 18.3 KB (**−47%**) | −36% | −5% | −5% |
| パン | Blue Noise | 11.92 → 11.51 | 0.733 → 0.692 | 48.3 → 26.8 KB (**−44%**) | **−53%** | −3% | −5% |
| アニメ風 | なし | 6.88 → 6.90 | 0.977 → 0.977 | 7.2 → 7.2 KB (0%) | −3% | 0% | −1% |
| アニメ風 | Blue Noise | 7.62 → 7.05 | 0.940 → 0.973 | 18.8 → 16.3 KB (−13%) | −23% | +4% | +1% |
| 白黒シルエット | なし | 2.60 → 2.60 | 0.886 → 0.886 | 0% | 0% | 0% | 0% |
| 白黒シルエット | Blue Noise | 3.00 → 2.65 | 0.824 → 0.872 | 23.4 → 13.7 KB (**−41%**) | **−49%** | −3% | −3% |
| testsrc2 | なし | 14.93 → 15.08 | 0.887 → 0.870 | 28.7 → 24.8 KB (−13%) | −16% | −4% | −5% |
| testsrc2 | Blue Noise | 15.32 → 15.31 | 0.875 → 0.868 | 52.1 → 39.3 KB (−25%) | −30% | −2% | −3% |
| mandelbrot | なし | 12.81 → 13.16 | 0.922 → 0.911 | 45.4 → 34.2 KB (−25%) | −15% | −6% | −5% |
| mandelbrot | Blue Noise | 13.15 → 13.45 | 0.905 → 0.898 | 50.2 → 38.3 KB (−24%) | −25% | −10% | −8% |

- GUI の既定 (Blue Noise) では、データ −13〜−44%、rect の呼び出し −23〜−53%、描画時間 −8〜+1%。色差 (ΔE2000) は 5 本中 4 本で良くなる (平坦な部分のディザの粒が 1 色になるため)。MS-SSIM はアニメ風・シルエットで上がり、パン (−0.04)・testsrc2・mandelbrot (−0.01) で下がる。
- 強さ 32 ではデータ −23〜−75%・描画時間 −1〜−17% まで減るが、mandelbrot の ΔE2000 が +1.1、パンの MS-SSIM が −0.06 になる。既定は画質がほとんど変わらない 16 にした。
- 呼び出しは減るが、置くブロックはあまり減らない。置くブロックを大きく減らすのは条件付き更新 (8.2) の役目で、この最適化は主に「同じ数のブロックを少ない箱・少ないデータで置く」効果。
- アニメ風・シルエットのディザなしは、もともと平坦で減色の結果がほぼ最適なので変わらない。
- 変換の時間: 512×288 で 1 フレーム約 170 ms 増える (CPU)。同時に動き探索を速くした (前のフレームを端で広げてずらした範囲を直接比べる。結果は同じで 2〜7 倍速い) ので、v6.6.0 と比べた変換全体は +26% (512×288・40 フレーム: 9.4 → 11.8 秒、`--block-rdo 0` なら 5.6 秒)。
- モックで再生すると、最初のキーフレームが箱にまとまるので rect 方式が選ばれ、1 tick のブロック数の上限 (4000 個) どおりに数 tick かけて置く (192×108 で 3 → 5 tick)。座標リストの方式は上限より大きな単位で置くので速く終わっていた。描画時間の見積もりは rect の方が小さく、上限は意図どおりなので変えていない。

**回転・反転したタイルの参照** (`benchmark/tile_orientation_study.py`): タイル辞書に「回転・反転 (8 通り) した形で貼る」参照を足したときの効果を、復元した盤面で見積もった。変わったタイルのうち、そのままでは辞書に無く回転・反転すると見つかるものは、Blue Noise では 0〜4.6% のデータ (タイル 4 / 8 の良い方、エントロピー符号化の前、動き補償なしで比べた上限)。ディザなしのアニメ風 (8.3%)・シルエット (19.3%、タイル 8) では大きいが、`--tile-size auto` が選ぶのは多くの場合タイル 4 (5.8〜8.3%)。データ形式とアドオンの変更 (v6.6 以前のアドオンでは再生できなくなる) に見合わないので見送った。ディザなしの白黒の映像が多いなら再検討する。

## 13. Phase 8.6: 構造物とクローンによる描画 (見送り)

**構造物** (`StructureManager.place`): 安定版 1.19.0 でも使えるが、実機の `bench` (2026-10-11、Windows) で 1 ブロック 2.31 µs と、座標リスト (1.45 µs) や箱 (1 回 15 µs + 1 ブロック 0.55 µs) より遅い。辞書のタイルの再利用も平均 1.1〜1.6 回 (6 章) なので、構造物を作る費用も回収できない。

**`cloneBlocks`** (`Dimension.cloneBlocks`、`CloneMode.ForceCopy` でコピー元と先の重なりも可): 安定版の Script API 2.10.0 から使え、2.10.0 が安定版になったのは Minecraft 26.50 (bedrock-samples のメタデータで確認。26.40 では beta)。使うには `manifest.json` の依存を 2.10.0 に上げる必要があり、26.50 より前の Minecraft ではアドオンが読み込めなくなる。リモコンのスライダーなど `@minecraft/server-ui` 2.x の引数も変わる。

効果の見積もり (`benchmark/clone_study.py`、128×72・60 フレーム・自動パレット・`--block-rdo 16`): 動きベクトルを持つ 8×8 ごとに、前の盤面のずらした範囲をコピーしてから残りの違いを置く場合と、変わるマスだけを置く場合 (座標リスト 1.42 µs/ブロック) を比べ、得になるブロックだけコピーしたときの描画時間の減り方。コピーの費用は未計測なので、1 回 15 µs + 1 ブロック c µs で試した:

| 映像 | ディザ | c = 0.1 µs | 0.2 | 0.3 | 0.5 | 0.8 |
|---|---|---|---|---|---|---|
| パン | なし / Blue Noise | −9.1% / −7.8% | −5.2% / −5.1% | −3.0% / −3.2% | −0.8% / −0.7% | 0% |
| testsrc2 | なし / Blue Noise | −9.3% / −6.4% | −5.1% / −3.7% | −2.5% / −2.1% | −0.4% / −0.5% | 0% |
| 白黒シルエット | なし / Blue Noise | −6.0% / −3.4% | −2.1% / −1.0% | −0.6% / −0.2% | −0.1% / 0% | 0% |
| アニメ風 | なし / Blue Noise | −1.6% / −2.0% | −0.1% / −1.0% | 0% / −0.4% | 0% / −0.1% | 0% |
| mandelbrot | なし / Blue Noise | −1.8% / −1.2% | −0.9% / −0.7% | −0.5% / −0.4% | −0.1% / −0.1% | 0% |

- コピーは変わらないマスも含めて 8×8 全体を書き直すのに、今の描画はもともと変わるマスだけを置いている。そのため、コピーが座標リストの 1/14 (0.1 µs) まで安くても −9% 以下、箱の 1 ブロックの費用 (0.55 µs) と同じくらいなら −1% 以下。
- 画面全体を 1 回でコピーする案 (パン専用) も、128×72 = 9216 マスのコピーが変わるマス (パンで 1 フレーム 700〜900 個) を置くより多くなる。
- アドオンが読み込める Minecraft の版を狭める代償に見合わないので、両方とも見送った。`cloneBlocks` が 1 ブロック 0.2 µs 以下だと実機で分かったら再検討する (そのときは `bench` に計測を足し、費用のモデルで使うかを決める)。

## 14. Phase 8.7: ホログラムの素材と入力

**ステンドグラスのパレット** (`--palette glass`、GUI の「ステンドグラス 16 色」): 16 色のステンドグラス (1.21.80 にもある) の色を、ほかのブロックと同じく公式テクスチャ (bedrock-samples 1.26.50.4) から測った。半透明なので、各画素をアルファで重みを付けて平均し、平均の不透明度 (どれも 0.46) も `mvcodec/block_colors.py` に書く。見える色は後ろにある物で変わるので、全ブロック・自動パレットには入れず、立体用の専用パレットにした。中まで詰まった立体では重なって暗くなるので、`--hollow` との組み合わせも案内している。発光ブロックだけのパレットは候補が 7 色しかなく、作っていない。

**AI の深度推定** (`scripts/make_depth_video.py`): Depth Anything V2 Small (Apache-2.0、約 100 MB) で動画から深度動画 (明るいほど手前) を作り、`--depth-video` に渡す。Sintel の予告編 (CC-BY 3.0、128×72・10 fps・12 秒・奥行き 16、手元の確認だけでリポジトリには入れない) で比べた:

| 奥行きの元 | 1 フレームに変わるマス | データ |
|---|---|---|
| 明るさ (既定) | 3038 | 191 KB |
| 深度推定 (そのまま) | 4240 | 175 KB |
| 深度推定 + 前のフレームと 3 割混ぜる (既定) | 3734 | 181 KB |
| 深度推定 + 明るさの範囲をゆっくり追う (0.1) | 5166 | 186 KB |
| 深度推定 + 前のフレームと 6 割混ぜる | 3942 | 189 KB |

- 明るさを奥行きにすると模様の凹凸にしかならないが、深度推定では人物が背景から手前へ浮き出る (斜め上から描いた絵で確認)。
- フレームごとの推定なので奥行きがちらつき、変わるマスは明るさより 23〜40% 多い。前のフレームと混ぜると −12% になる。範囲をゆっくり追いかけると、場面の切り替わりで範囲が合わず、かえって増えた。
- CPU (Windows) で 1 フレーム約 0.5 秒。時間方向に一貫した推定をする Video Depth Anything の出力も、そのまま `--depth-video` に使える。

**チャンクにそろえた設置** (`/scriptevent <接頭辞>:setup align`): ブロックを置き替えると、そのブロックがあるサブチャンクが描き直されてプレイヤーへ送られるので、スクリーンがまたぐチャンクを減らせば負荷が減る見込み。立つ位置から東西・南北に最大 15 ブロックずらし、またぐチャンクが一番少ない位置に置く。チャンクの数 (16 通りの立つ位置の平均 → そろえた後):

| 大きさ | 平均 | そろえた後 |
|---|---|---|
| 64×36 | 15.7 | 12 (−24%) |
| 128×72 | 48.6 | 40 (−18%) |
| 128×128 | 79.9 | 64 (−20%) |
| 256×144 | 168.3 | 144 (−14%) |

ゲーム内の効果 (描き直し・送り直しの時間) はモックでは測れないので、既定では今までどおり足元に置き、`align` を付けたときだけずらす。

## 16. Phase 9: 映像に合わせた自動調整

**9.1 最適化の強さの自動選択** (`--block-rdo auto`、既定): 8.5 の強さを固定 (16) にすると、実写やパンで MS-SSIM が −0.04 と大きく下がった。そこで、候補ごとの色の誤差と費用を一度だけ計算し、強さ 64 / 32 / 16 / 8 / 4 / 2 / 1 の順に選び直して、増える色の誤差 (減色のままと比べた、ぼかした OkLab の二乗誤差の 1 画素あたりの平均) が予算以内の一番強いものを使う。選び直しは配列の argmin だけなので、変換の時間はほとんど増えない。

強さ 16 のときの増える誤差の平均は、実写 5.1・パン 2.6・mandelbrot 1.9・アニメ予告編 1.4・CG 予告編 1.1・アニメ風 / シルエット / testsrc2 は負 (ぼかした誤差はかえって減る)。予算を 1〜3 で比べた (128×72・自動パレット 64 色・Blue Noise、最適化なしと比べた変化):

| 設定 | データの削減 (8 本の平均) | MS-SSIM の一番大きい低下 |
|---|---|---|
| 固定 16 | −34% | −0.041 (パン・実写) |
| 固定 32 | −51% | −0.093 (実写) |
| auto 予算 1 | −29% | −0.018 |
| auto 予算 2 | −34% | −0.018 |
| auto 予算 3 (既定) | −37% | −0.021 |

固定の 16 と同じかそれ以上データを減らしながら、画質が一番落ちる映像での低下を半分にできる。平坦な映像 (アニメ風・シルエット・testsrc2) では強さ 64 が選ばれて固定 16 より減り、実写・パンでは弱い強さが選ばれる。

**9.2 パレットの色数の自動選択** (`--palette-colors auto`、既定): 自動パレットの色数を 64 に固定すると、色の少ない映像でも 64 色のディザの粒・ちらつき・座標リストの呼び出し (色の数) が残る。色数を固定で減らすと (64 色と比べて):

| 映像 | 32 色 | 16 色 |
|---|---|---|
| アニメ風 | データ −10%・ΔE +0.07 | −25%・−0.01 |
| パン | −5%・+0.17 | −41%・+0.11 (ぼかした ΔE +1.03、MS-SSIM −0.029) |
| 実写 | −10%・+0.10 | −27%・+0.67 |
| アニメ予告編 | −17%・+0.45 | −35%・+0.91 |
| シルエット | −36%・−0.03 | −37%・−0.03 |

効果も画質への影響も映像で大きく違うので、シーンごとに選ぶ。K-Means を 24 / 32 / 48 / 64 色で行い、サンプルした画素と一番近いブロックの OkLab の距離の平均が、64 色のときの 1.05 倍以内に収まる一番少ない色数を選ぶ。16 色はパンで崩れたので候補にしない。

**9.1 + 9.2 の結果** (v6.8.0 の既定 = 強さ 16・64 色と比べて、8 本):

| 映像 | データ | 描画時間 | 座標リストの呼び出し | ΔE2000 | MS-SSIM |
|---|---|---|---|---|---|
| アニメ風 | −36% | −14% | −44% | +0.29 | −0.013 |
| パン | +11% | −3% | −25% | +0.21 | +0.016 |
| testsrc2 | −41% | −16% | −41% | +0.35 | −0.005 |
| mandelbrot | −8% | −14% | −34% | −0.02 | −0.002 |
| シルエット | −46% | −4% | −48% | −0.05 | +0.013 |
| 実写 | +6% | −7% | −29% | −0.20 | +0.019 |
| CG 予告編 | −10% | −8% | −46% | +0.11 | −0.007 |
| アニメ予告編 | −2% | −4% | −27% | +0.22 | −0.008 |

- 描画時間と呼び出しはすべての映像で減る (色が減ると座標リストの呼び出しが減り、ディザの粒も減る)。
- データは平均 −16%。パン・実写は、画質を守るために最適化を弱めるぶん +6〜+11% 増えるが、v6.8.0 で一番落ちていた MS-SSIM が戻る。

**2.5D の立体の色の平面への適用** (v6.10): relief / extrude / inflate を 2.5D (色の平面 + 値の平面) で送るとき、色の平面にも同じ最適化をかける。値の平面 (形) は変えない。色の平面の 1 マスを変えると、その列の厚みのぶんのブロックを置き直す (rect 方式では奥行き方向の 1 個の箱) ので、置く費用を列の厚みで重み付けし、空の列 (厚み 0) は見えないので色の誤差に数えない。

最適化なしと既定 (auto) の比較 (128×72・奥行き 12・自動パレット・ディザなし。色差は正面から見た一番手前のブロックの側面の色と元の映像の ΔE2000):

| 映像 / モード | データ | 描画時間 | 置くブロック | 色差 |
|---|---|---|---|---|
| シルエット / extrude | −3% | +1% | 0% | 2.43 → 2.82 |
| シルエット / inflate | −1% | 0% | 0% | 2.43 → 2.57 |
| アニメ風 / relief | −4% | 0% | +1% | 6.61 → 6.87 |
| mandelbrot / relief | −16% | 0% | 0% | 9.23 → 9.92 |
| 実写 / relief | −22% | −10% | −10% | 5.94 → 6.33 |
| CG 予告編 / relief | −13% | −1% | −1% | 4.73 → 4.87 |

平面スクリーンより効果は小さい (立体は値の平面のデータと、形が変わる列の置き直しが残るため)。実写のレリーフではデータ −22%・描画時間 −10%。

## 17. 実機の録画との比較 (v6.11)

利用者がゲーム内で録画した映像 (アニメの MV、256×144・5fps・ウルトラ、GPU で変換。第三者の著作物なので、分析は手元だけで行い、
リポジトリには何も入れていない) を、元の動画・変換したデータと照合した。

**照合の方法**: 録画の各コマを、スクリーンの四隅 (ECC で微調整) で 256×144 に戻し、ブロックの中央の色を取る。ゲームの明るさは
色の線形補正で合わせ、コマ番号は「戻らない」制約の動的計画法で対応づける。

**わかったこと**
- 再生のタイミングは正常 (音声に合わせて進み、理想の位置との差は ±1 秒程度)。描画の遅れで崩れているのではない。
- 録画に見える四角いムラ・前の映像の残りは、変換したデータにそのまま入っていた。原因は 2 つ:
  1. **GPU の減色に古い更新制御が残っていた**: 1 フレームに置き直す画素数の上限 (場面の変化に応じて 5〜35%)、変化の小さい画素の
     据え置き、前フレームの誤差の持ち越し。ブロックモードの最適化 (12 章) を入れる前の仕組みで、CPU の減色からは外していたが
     GPU には残っていた。上限を超えた画素は前の映像のまま残る。
  2. **自動パレットの使い回しの判定が最初のコマだけ**: 黒い画面から始まる別々の場面 (この動画では 3 つ) が、最初の場面の
     パレットを使っていた。
- 色数の自動選択 (16 章、許す倍率 1.05) は、色の多い場面でも 24 色を選ぶことが多かった。127 色に固定すると、一部の場面で
  ぼかした色差がほぼ半分 (7.13 → 3.80) になった。ディザ後にぼかした誤差・誤差の大きい画素 (上位 10%・90 パーセンタイル) で
  選ぶ方法も試したが、どれも少ない色数を選び悪化した。

**変更** (v6.11): GPU の減色は各フレームを忠実に減色し、CPU と同じ条件付き更新 (`--temporal-hysteresis`) だけを行う
(置き直す量の調整はブロックモードの最適化に任せる)。パレットの使い回しは、パレットを作るのに使う全部のコマで判定する。
色数の許す倍率を 1.02 にする。

この動画 (元の動画と比べて、ゲームに入っていた v6.10.0 のデータ → v6.11):

| | ぼかした色差 | MS-SSIM | データ | 描画時間 (推定、1 コマ) |
|---|---|---|---|---|
| v6.10.0 (GPU) | 6.19 | 0.821 | 1,821 KB | 5.7 ms |
| GPU の減色を修正 | 5.75 | 0.863 | 1,933 KB | 6.0 ms |
| + パレットの判定を修正 | 5.63 | 0.861 | 1,933 KB | 6.0 ms |
| + 色数の倍率 1.02 (v6.11) | **5.45** | **0.862** | 2,112 KB | 6.2 ms |

8 本の評価用映像 (128×72・10fps、GPU。v6.10.0 の減色・倍率 1.05 → v6.11。どちらもパレットの判定は修正後):

|---|---|---|---|---|
| アニメ風 | 6.20 → 6.19 | 0.851 → 0.863 | 26 → 26 KB | +6% |
| パン | 10.88 → 8.03 | 0.436 → 0.757 | 13 → 50 KB | +174% |
| testsrc2 | 14.43 → 13.64 | 0.862 → 0.881 | 47 → 45 KB | +12% |
| mandelbrot | 10.24 → 7.96 | 0.814 → 0.848 | 47 → 61 KB | +33% |
| シルエット | 2.61 → 2.61 | 0.884 → 0.886 | 12 → 11 KB | 0% |
| 実写 | 4.86 → 3.92 | 0.899 → 0.958 | 78 → 117 KB | +65% |

画質はすべての映像で同じか良くなる。パンと実写で描画時間とデータが大きく増えるのは、v6.10.0 の GPU の減色が置き直す画素を

**残る課題**: なめらかなグラデーションで、8×8 を 1 色で塗る判定 (solid_mean) が四角く見える。ブロックモードの最適化の誤差は

## 18. 実写の映像での色合い (v6.12)

実写の評価用映像を 8 本に増やした (Xiph の標準テスト映像 4 本: park_joy・ducks_take_off・old_town_cross・in_to_tree、
Tears of Steel の 4 場面: バルコニー・室内の 3 人・運河の通り・顔のアップ。どれも手元だけで使い、リポジトリには入れない)。
128×72・10fps と 256×144・5fps の 16 本で、v6.11.0 の既定 (GPU) と比べた。

**わかったこと**: 一番目立つ崩れは **色合いのずれ** だった。暗い緑の木の葉・芝生が、明るさの近い茶色 (原木) や青緑のブロックに
なる (in_to_tree のぼかした色差 12.1、ほかの倍)。原因は 2 つ:
1. 暗い緑のブロックが少ない。乾燥した昆布ブロックは、名前に kelp (植物の昆布を除く語) を含むため候補から漏れていた。
2. 減色は OkLab の距離で一番近いブロックを選ぶが、明るさ (L) と色合い (a, b) を同じ重さで比べるので、色合いが大きく違っても
   明るさの近いブロックが選ばれる。CPU の減色はさらに RGB の距離 (Pillow) で選んでいた。

**変更** (v6.12):
- 乾燥した昆布ブロックを候補に入れる (不透明なブロック 197 → 198、自動パレットの候補 190 → 191)。
- 減色で、OkLab の色合い (a, b) の差を 2 倍に重く見る (`mvcodec/color.py` の `CHROMA_WEIGHT`)。CPU の減色も同じ OkLab の
  最近傍にした (以前は Pillow の RGB。実写 16 本でぼかした色差 −11%、変換の速さは同じ)。
- ブロックモードの最適化の色の誤差も、色合いを 1.5 倍に重く見る (`mvcodec/block_rdo.py` の `RDO_CHROMA_WEIGHT`)。

重みの比較 (実写 16 本、減色の重み 1 → 2 / 2.5 / 3): ぼかした色差 −7% / −10% / −11%、MS-SSIM −0.008 / −0.017 / −0.026。
2.5 以上は明るさの細部 (MS-SSIM) の落ち方が大きいので 2 にした。最適化の重みは 1.5 で −3% (2 では −4% だが、木の映像の
MS-SSIM が −0.05)。パレットを作る K-Means の色空間 (`--palette-space oklab`) は差が小さかったので変えない。

v6.11.0 → v6.12 (GPU、元の映像と比べて):

| 映像 | ぼかした色差 (128×72 / 256×144) | MS-SSIM の差 | データ | 描画時間 |
|---|---|---|---|---|
| park_joy (公園の木と芝生) | −22% / −22% | −0.01 / −0.02 | −6% / −5% | −4% / −3% |
| in_to_tree (木へのズーム) | −19% / −18% | −0.03 / −0.03 | −5% / −5% | −4% / −1% |
| old_town_cross (街並み) | −17% / −14% | 0.00 / 0.00 | −3% / −12% | 0% / −5% |
| ToS 運河の通り | −17% / −17% | 0.00 / 0.00 | −9% / −8% | −2% / −1% |
| ToS 室内の 3 人 | −14% / −12% | 0.00 / 0.00 | −3% / −5% | −2% / −2% |
| ToS 顔のアップ | −11% / −10% | 0.00 / −0.01 | −5% / −6% | −3% / −2% |
| ToS バルコニー | −4% / −7% | 0.00 / 0.00 | −5% / −2% | −4% / −1% |

MS-SSIM が少し下がる (明るさの細部より色合いを優先するため)。評価用 8 本 (合成・アニメ・CG を含む) では
ぼかした色差 平均 −5% (一番悪くて +0.3%)、MS-SSIM はほぼ同じ (平均 −0.0004)、データ −5%。
利用者のアニメ MV (17 章) では 5.45 → 5.09 (−7%)。

**残る課題**: 茂った木の葉の暗い緑は、まだ元より茶色寄り (暗い緑のブロックが少ない)。水面や葉の細かい明るさの模様は
色数の少ないパレットとディザでは再現しにくい。

## 19. まだ試していないジャンルでの評価 (v6.13)

パブリックドメイン、白黒) の 2 場面、自作の 3 本 (歌詞動画風の文字、スライド・UI 風の画面、ネオン風の光)。
128×72・10fps と 256×144・5fps の 24 本。

**わかったこと**: 平均の数値は大きく崩れていないが、見た目では **局所的な崩れ** が目立った: スライドの文字の一部が白い
四角で消える、雪山・白い壁・歌詞の背景のグラデーションに灰色の 8×8 が残る。ブロックモードの最適化 (12 章) を止めると
すべて消えるので、最適化の判断が原因。強さの予算 (`--rdo-budget`) は **フレーム全体の平均** で見るため、動きの少ない画面ほど、
いくつかのブロックの大きな崩れが平均に埋もれていた (強さはほとんどのフレームで最大の 64 になっていた)。

**変更** (v6.13): 候補ごとに、1 つのブロックで増える色の誤差に上限を付ける (`--rdo-block-cap`、既定 5。1 画素あたり、
`--rdo-budget` と同じ単位)。上限を超える候補 (前のフレームのまま・1 色・2 色など) は、そのブロックでは使わない。

試したもの (ジャンル 24 本、v6.12.0 の既定と比べて):

| 方法 | ぼかした色差 | MS-SSIM | 誤差の大きいマスの上位 0.1% | データ | 描画時間 |
|---|---|---|---|---|---|
| ぼかさない誤差の重み 0.1 → 0.3 | −0.4% | +0.006 | 0% | +8% | +6% |
| 同 1.0 | +0.1% | +0.009 | +2% | +13% | +10% |
| 上限 10 | −2.1% | +0.003 | −6% | +17% | +4% |
| 上限 7 | −3.9% | +0.005 | −8% | +23% | +7% |
| **上限 5 (採用)** | **−5.0%** (24 本すべて改善) | **+0.007** | **−10%** | +29% | +9% |
| 上限 5 + 強さの候補に 128〜1024 を追加 | −5.0% | +0.007 | −10% | +29% | +9% |

ぼかさない誤差を重くすると、ディザの粒まで誤差に数えて効果が出なかった。上限 10 ではスライドの文字はまだ消える。
強さを上げてもデータは減らない (強さ 64 の時点で、使える安い候補はすべて選ばれている)。

ほかの映像 (v6.12.0 → 上限 5): 実写 16 本 ぼかした色差 −2.6%・MS-SSIM +0.011・データ +12%・描画時間 +6%。
評価用 8 本 −1〜−5% (すべて改善)・データ +5〜21%。利用者のアニメ MV (17 章) は色差 5.09 → 4.79、MS-SSIM
0.853 → 0.872、データ +58% (上限 10 なら 4.93・0.864・+33%)、描画時間 +5%。データを抑えたいときは `--rdo-block-cap 10`。

ジャンルごとの v6.12.0 の弱点 (上限 5 の後も残るもの): 舞台照明のダンス (暗い舞台の人物、MS-SSIM 0.82)、アメフト
(芝の緑が黄土色寄り、MS-SSIM 0.86)、歌詞動画風 (なめらかなグラデーション、ぼかした色差 5.8)、スライドの色付きの見出し帯
(ちょうど合うブロックが無い色はディザの粒が目立つ)。

## 20. パターンディザ (v6.14)

v6.13.0 の実機の録画 (利用者のアニメ MV) で目立った残りの弱点は 2 つ: **暗いグラデーションのザラつき** (夜空や暗い背景に
灰色・紫のブロックの粒) と、**肌の色が白っぽくなる** こと。どちらも Blue Noise のディザが、明るさ (RGB の 3 つに同じ値) に
一定の揺らぎ (±32) を足してから一番近い色を選んでいたのが原因:
- 暗い所では ±32 が見た目に大きく、近い色のブロックがあっても離れた色に飛ぶ。
- 揺らぎは明るさの方向だけなので、色合いは混ざらない。肌 (246, 218, 201) はどのブロックより明るく、白に近いブロック
  (薄いオークの板材) 1 色になっていた。

**試したもの**: (1) 2 色を混ぜるディザ (各画素で混ぜると元の色に一番近くなる 2 色と割合を求める)。MS-SSIM は上がったが、
2 色の間に入らない色が段差になり、なめらかなグラデーションや木の葉でぼかした色差が +8〜11% 悪化。
(2) **パターンディザ (Knoll)**: 誤差を足しながら一番近い色を 8 回選んで候補を作り、明るさの順に並べて Blue Noise の値で
1 つ選ぶ。候補の平均 (線形の明るさ) が元の色に近づくので、明るさも色合いも 2 色に限らず混ざる。ちょうど合う色のある所では
粒が出ない。誤差を足す割合は 0.5 (1.0 より MS-SSIM が高い)。

**変更** (v6.14): `--dither-method blue_noise` (既定) をパターンディザにした (CPU は `mvcodec/color.py` の
`knoll_dither_indices`、GPU は `knoll_dither_torch`。結果は同じ)。輪郭 (知覚最適化のマスクが 0.5 未満) では混ぜない。
DirectML は並べ替え (argsort) が遅い (8×36864 で約 19 ms) ので、候補の順位を比べて数える方法にして 1 フレーム 38 → 10 ms。

v6.13.0 → v6.14 (GPU、元の映像と比べて):

| | ぼかした色差 | MS-SSIM | データ | 描画時間 |
|---|---|---|---|---|
| ジャンル 24 本 | −7.6% (全本改善) | +0.013 (全本改善) | +2% | +5% |
| 実写 16 本 | −8.7% (全本で −4.8% 以上) | +0.011 | +3% | +5% |
| 利用者のアニメ MV | 4.79 → 4.53 | 0.872 → 0.889 | +1% | — |

変換時間は +7% (アニメ MV 1026 フレームで 116 → 124 秒)。肌は 4 種のブロック (的・なめらかなクォーツ・薄いオークの板材・
模様入りの砂岩) の混ざりになり、1 色で塗るより元の色に近い (OkLab の差 3.05 → 2.29)。肌はどのブロックより明るいので
ぴったりにはならない。口の中のような小さな赤い面は、オレンジの粒が混ざって見えることがある。

## 21. Phase 10.1: データの文字列化 (v6.15)

v6.11〜v6.14 で画質を上げた分、利用者のアニメ MV のデータは 1.8 → 3.5 MB に増えた (主に 19 章の上限)。中身を調べると、
アドオンの JS ファイル 3,480 KB のうち、符号化したデータそのものは 2,124 KB だけで、残りは **バイト列を JS の文字列にする
ときの膨らみ** だった。15 ビットずつ `0x1000 + 値` の文字にしていたが、その文字は UTF-8 のファイルで 3 バイトになる
(24 / 15 = 1.6 倍)。

| 文字列化 | JS ファイル | .mcaddon (zip) | QuickJS の中 | JS のデコード (Node) |
|---|---|---|---|---|
| 15 ビット/文字 (v6.14 まで) | 3,480 KB | 2,206 KB | 1.07 倍 (16 ビットの文字) | 33.9 ms |
| **base64 (v6.15)** | **2,912 KB (−16%)** | **1,865 KB (−15%)** | 1.33 倍 (8 ビットの文字) | **22.6 ms** |
| Z85 (試算) | 2,737 KB (−21%) | 2,020 KB (−8%) | 1.25 倍 | — |

CurseForge に出るのはダウンロード (zip) の大きさなので、zip でもよく縮む base64 にした。画質・置くブロックは変わらない
(同じバイト列)。デコーダは先頭の `"B:"` で見分けるので、以前のデータも読める。

まだ縮む余地: 同じデータを xz で圧縮すると 1,734 KB (今のハフマン符号は 2,124 KB) で、文脈を使う符号化なら 2 割ほど
縮む見込みがある。ただしゲーム内の復号が重くなるので、QuickJS での速さを測ってから決める。

## 22. Phase 10.2: 確率を学習する区間符号 (v6.16)

21 章の「まだ縮む余地」を調べた。ハフマン符号の入れ物の 8 個のストリームを、記号ごとに文脈を変えた適応的な
符号化で符号化したときの理論サイズを比べると (評価用の映像、`sintel_trailer` 128×72)、縮むのはほとんどランの色と長さだった。

| 文脈 (ランの色、7 ビットの木) | 色のストリーム |
|---|---|
| ハフマン (今) | 122.7 KB |
| 文脈なしの適応 | 108.5 KB |
| **直前のランの色** | **96.6 KB (−21%)** |
| 直前 2 個の色 | 127.1 KB (文脈が多すぎて学習が追いつかない) |
| 復元した盤面の上の画素 (参考) | 89.0 KB |

上の画素を文脈にするとさらに 8% 縮むが、入れ物を開くときに盤面の復元 (動き補償・タイル) も同時に行う必要があり、
今の「開いてから復元する」作りを大きく変えることになるので見送った。長さ・間隔の文脈 (直前の長さ・区分・色が同じか) は
どれも ±0.2% で差が出なかった。

**採用した方式** (`mvcodec/rangecode.py`、入れ物の種類 2): LZMA と同じ 2 値の区間符号 (確率 11 ビット) とビット木。
ランの間隔は LZMA の距離と同じ「ビット長 + 次の 1 ビット」の区分 (6 ビット) と残りのビット、長さは 6 ビットの木、
色は直前の色ごとの 7 ビットの木 (学習を速く)、ヘッダ・動きベクトル・タイルは v5 のバイトを種類ごとの 8 ビットの木。
表を送らないので短い GOP でも損をしない。

| 映像 | ハフマン | 区間符号 |
|---|---|---|
| 評価用 8 本の合計 | 628 KB | 521 KB (**−17%**、−9〜−22%) |
| 実写 256×144 (ducks_take_off) | 589 KB | 496 KB (−16%) |
| 利用者のアニメ MV (256×144・5fps) | 2,176 KB | 1,624 KB (**−25%**、xz の 1,734 KB より小さい) |
| 同、.mcaddon の中の zip (base64) | 1,856 KB | 1,601 KB (−14%) |

**代償は展開の速さ**: Node の JIT なし (QuickJS に近い) で、出力 1 MB あたり ハフマン 0.12 秒 → 区間符号 0.75 秒。
MV 全体 (約 4 分) で 2.4 秒、再生中は先読み (`prefetchGop`) で tick に分けて行うので 1% 程度。yield の間隔は
4 KB ごとに短くし、1 回の処理は 4.4 ms 以下 (JIT なし)。とても大きな画面で展開が追いつかないときのために
`--entropy-coder huffman` で以前の入れ物も作れる。変換の時間は MV で +8 秒。

## 23. 白い場面のまだら (v6.17)

v6.15 の実機の録画で、白い背景のぼかし (ビネット) の場面に、少し赤みのある白・青みのある白のブロックが 8×8 ごとに
並んで、まだらな四角が目立った。

**原因 1: 8×8 を単色・2 色で塗る候補** (`solid_mean` / `solid_mode` / `two`、12 章)。最適化を切る (`--block-rdo 0`) と
まだらは出ず、ディザの粒になる。候補ごとに外して比べると、単色の 2 つと 2 色の両方がまだらを作っていた。
ブロックの平均の色の誤差を足す・上限を付ける案は効かなかった (8×8 の平均の色はどの白でも元の色に近く、
まだらに見えるのは隣の 8×8 との境目が揃うため)。
**直し方**: 元の映像の 8×8 の平均の色が上下左右の 8×8 と 0.8〜8 (OkLab × 100、色合いは 1.5 倍) 違う所
(なめらかなグラデーション) では、単色・2 色の候補を使わない。差が大きい所は輪郭、差が無い所は平らな面なので今までどおり。

**原因 2: 無彩色の明るい灰色のブロックが無かった**。色の表を作るとき、方解石 (225, 226, 222)・鉄ブロックが、
青白いオークの板材 (229, 219, 218、少し赤み) と「ほぼ同じ色」として除かれていた。色合い (a, b) だけの距離が 1 以上なら
別の色として残すようにした (`DEDUPE_CHROMA_DISTANCE`)。不透明なブロック 198 → 221 色、自動パレットの候補 191 → 214 色。

| v6.16.0 と比べて | ぼかした色差 | MS-SSIM | データ | 描画時間 |
|---|---|---|---|---|
| ジャンル 24 本 (色の表だけ) | −0.8% | +0.0005 | +2.4% | +1.3% |
| ジャンル 24 本 (**両方**) | **−2.0%** (最悪 +4.2%: アメフト) | +0.0001 | +4.4% (最大 +21%: スライド) | +1.2% |
| 実写 16 本 (両方) | **−1.2%** | +0.0039 | +1.9% | +1.0% |
| MV の白い場面 (31 コマ) | まだらな四角がほぼ消える | — | +22% | — |

境目を 1.5 にしても結果はほぼ同じ (ジャンル −1.7%・+3.9%)。アメフトの芝の色差 +4% は色の表を変えた影響
(新しいブロックで自動パレットの選び方が変わる)。

**見送ったこと**:
- スライドの青い見出し帯の粒: その色 (32, 99, 214) に一番近い不透明なブロックでも色差 10.7 (OkLab × 100) あり、
  混ぜるしか近づける方法が無い。
- アメフトの芝が黄土色寄りに見える: 芝の部分の平均の色は元の映像と同じ (a −2.6・b +4.1 と a −2.6・b +3.7)。
  黄色みのある緑のテラコッタと灰色の混ぜ方で、そう見える。

## 24. 混ぜて表す色をパレットに入れる (v6.18)

暗い舞台の人物 (Dancers) で、男性の暗いオリーブ色のズボン (39, 37, 26) が茶色のブロックになっていた。自動パレットは
K-Means の代表色ごとに「一番近いブロック 1 つ」を選ぶので、近いブロックの無い色 (一番近い黒のテラコッタでも
OkLab × 100 で 5.9) は、混ぜれば近くなる組 (暗い緑の木材 + 黒など) があってもパレットに入らず、パターンディザ
(20 章) が混ぜる相手を持てなかった。

**直し方** (`mvcodec/auto_palette.py`): 代表色に一番近いブロックが `MIX_THRESHOLD` より遠いときは、近い 24 個の
ブロックの組のうち、線形の明るさで 1/8 ずつ混ぜたときに代表色に一番近くなる 2 つを入れる (大きいクラスタから順に、
色数の上限まで)。

| v6.17.0 と比べて | ぼかした色差 | MS-SSIM | データ | 描画時間 |
|---|---|---|---|---|
| ジャンル 24 本、しきい値 **2** | **−1.6%** (最悪 +1.9%) | +0.0011 | +0.2% | +0.4% |
| 実写 16 本、しきい値 **2** | **−3.9%** (最悪 +1.4%) | +0.0018 | +1.9% | +2.1% |
| ジャンル / 実写、しきい値 3 | −0.9% / −2.3% | +0.0013 / +0.0015 | −0.2% / +0.1% | 0% / +0.4% |
| ジャンル / 実写、しきい値 4 | −0.9% / −2.0% | +0.0006 / +0.0011 | 0% / −0.3% | +0.2% / −0.2% |

よく効いたのは実写の木 (in_to_tree −8%)・街並み (old_town_cross −6%)・アメフト (−7%)。Dancers のズボンは画面の中で
小さく、K-Means の代表色そのものが暗い色にまとめられるので、ほとんど変わらなかった (−1.4%〜+1.1%)。
ブラウザ版 (PyTorch が無いとき) は、代表色を使わない数え上げで選ぶので変わらない。

**見送ったこと: 赤い面に混ざるオレンジの粒**。アニメ MV の赤い背景 (193, 23, 32) は、どのブロックより鮮やかで、
パターンディザが赤い釉薬付きテラコッタ・赤の羊毛に明るいオレンジのコンクリートを少し混ぜて近づけている。
誤差の蓄積に上限 (線形の明るさで 0.05〜0.2) を付けるとオレンジは消えるが、ぼかした色差が +3〜5% 悪くなった
(平均の色が元から離れる)。

## 25. 視点に合わせた立体のだまし絵 (Phase 12、v6.20)

Java 版で、マップアートをプレイヤーの視点に合わせて描き直し、人物が立体に見える動画がある (利用者が共有。手元で
見ただけ)。コマを調べると、人物は立体の模型ではなく床と壁に描いた絵で、真上から床を見ると人物が引き伸ばされていた。

**作り** (`--view anamorphic`、`codec.js` の `projectToStage`):
- 立体 (.vox・relief・extrude・inflate) の人物はワールドに置かない。見ている人 (舞台の中央に一番近いプレイヤー) の
  目の位置 (`getHeadLocation`) から人物を見たとおりに、舞台の面へ塗る。正しく見えるのはその 1 人だけ。
- 舞台は床と 3 枚の壁 (後ろ・左・右) の、手前と上の開いた箱。壁の高さは人物の 1.5 倍、左右は人物の高さの 0.75 倍ずつ広げる。
- 外から見える面のうち目の方を向いた面を持つブロックだけを、目に近い順に写す。1 つのブロックの写る範囲は 8 つの角を
  通る視線が最初に当たる面から求め、範囲のまだ塗っていないマスについて、マスの中心から目への視線がそのブロックを
  通るか (箱との交差) を確かめる。近い順は「軸ごとに目に近い順に並べた入れ子の順」: 目からの視線は各座標が単調に
  変わるので、あるブロックを隠すブロックは、どの軸でも目に近いか同じで、この順で先に来る (並べ替えは整数のキーで 1 回)。
- 再生中・一時停止中・再生後も、目が 0.25 ブロック動けば描き直す (フレームを描かない tick に、その tick のうちに)。
  変わったマスを探す範囲は、人物を塗った行と列 (と、置き終えていない前の描画の範囲) だけ。

**計測**:

| | 結果 |
|---|---|
| 目から見た舞台と、人物を直接見た絵の一致 (5 か所) | 93〜94% (残りはブロックの境目。1 ブロック = 1 色) |
| 実機 (Windows)、高さ 56 の人物 | 10.13 fps (目標 10)・遅れ 1 / 40 フレーム・1 フレーム 26.7 ms |
| 実機、高さ 96 の人物 | 8.53 fps・TPS 17.9・110 ms (重すぎる。高さ 64 くらいまで) |
| モック (JIT なし) の 1 フレーム、だまし絵 / 同じ人物を立体で置く | 5.8 ms / 5.8 ms (重さは普通の立体と同じ。多くは復元) |

最初の試作は後ろの壁と床だけで、実機では正面からは立体に見えたが、真横や斜め上からは人物が欠けた (視線が後ろの壁にも
床にも当たらない)。正面から ±60° までは人物が 100% 写るが、85° では 15〜66% だった。左右の壁を足すと、箱の中か手前から
見る限り 85° でもほぼ全部写る。

**背景の映像** (v6.21): 見本では後ろの壁に MV の背景が流れている。背景の映像を後ろの壁と同じ大きさ (幅 stageWidth ×
高さ wallHeight) の平面の動画として同じアドオンに入れ (一覧には出さない)、人物のデータの `stage_background` で指す。
再生では同じ時計で背景の映像のフレームを復元し、後ろの壁の盤面にした上に人物を写す (パレット番号は 20000 からに
ずらし、自動パレットの GOP が変わったら背景のマスだけ置き直す)。背景の映像の方が長ければ人物のアニメを繰り返し、
音声は背景の映像のものを鳴らす。後ろの壁の大きさは人物を変換するまで分からないので、背景の映像は人物の後に変換し、
縦横比が違えばはみ出した所を切る (`--fit cover`)。

**見送り・未対応**: 見る人が箱の外の横にいるとき (手前の壁が邪魔になる)、2 人以上が同時に見るとき。Java 版の地図
(1 枚 128×128 点) と違い、Bedrock は地図をスクリプトから塗れないので 1 ブロック = 1 点になる。
