## 1. 画像モードの時計の同期

### 1.1 今の作り

再生の時計は、サーバーとクライアントで別々に数えています。

| 役 | 時計 | 場所 |
|---|---|---|
| サーバー (スクリプト) | 再生中の tick の数。`state.playTicks++` を毎 tick (`system.runInterval(..., 1)`)。位置 = `playTicks / 20` 秒 | `image_mode/image_main.js` |
| クライアント (Molang) | エンティティの年齢 `q.life_time` から作る時計 `v.t = (floor(q.life_time * 20) + q.frame_alpha) / 20` | `image_mode/rp.py` の `pre_animation`、SPEC.md |
| 合わせ方 | サーバーが 20 tick ごとに `frame` (今のコマ) と `seq` (通し番号) をエンティティのプロパティ (int、`client_sync`) に書く。クライアントは `seq` が変わった時刻を `base_time`、そのときの `frame` を `base_frame` にして、`base_frame + (v.t - base_time) * fps` で進める | 同上 |
| 音声 | 4 秒のチャンク。サーバーの位置がチャンクの頭から 0.3 秒以内のときだけ、全員に `playSound` で鳴らす。止めるのは `stopsound` コマンド | `updateAudio` |
| 一時停止・再開・シーク | サーバーが `pausedFrame` や `playTicks` を置き直し、すぐ `frame` と `seq` を書く | `pause` / `resume` / `seek` |
| 途中で入った人 | `playerSpawn` で、チャンクの頭から 1 秒以内なら今のチャンクを鳴らす。プロパティの書き直しはしない | `playForLateJoiner` |

### 1.2 問題の根本

**1. 時計が 2 つあり、合わせ直しは「飛ばす」だけ。** 合わせ直しで、クライアントは `base_frame` をそのまま入れ替えます。2 つの時計の進みが違うと、1 秒ごとに映像が前後へ飛びます。ずれを少しずつ戻す処理はありません。

**2. サーバーの時計は TPS に比例して遅れる (見込み)。** `playTicks` は tick の数なので、TPS が 10 ならサーバーの 1 秒は実時間の 2 秒になります。

- 映像: クライアントの時計が実時間で進むなら、1 秒ごとに後ろへ飛びます。TPS 10 なら、実時間の 2 秒ごとに約 1 秒戻ります (見込み)。
- 音声: チャンク (4 秒) は実時間で鳴ります。次のチャンクはサーバーの時計で 4 秒後、つまり実時間の 8 秒後に始まるので、約 4 秒の無音が続きます (見込み)。
- 未確認の前提: クライアントの `q.life_time` が、サーバーの TPS が落ちたときも実時間で進むか。シングルプレイ (同じプロセスの中のサーバー) と BDS で違う可能性があります。**実機での計測が最初の作業です。**

**3. 合わせ直しのときに、プロパティの古さを知る手段が無い。** `frame` は書いた時点のコマで、クライアントは「見た時刻」を起点にします。そのため、遅れて見た人は書いてから見るまでの時間だけ遅れます。

- 途中で入った人、チャンクを読み直した人、スクリーンに近づいて描画が始まった人は、最大で約 0.95 秒 (19 tick) 遅れます。次の合わせ直しで前へ飛びます。
- サーバー側の `entityLoad` では書き直します。ただしクライアントだけが読み込んだとき (すでにサーバーで読み込まれている画面に、人が入ってきた) は書き直しません。

**4. 一時停止の位置はサーバーの位置。** クライアントが先に進んでいれば、一時停止の瞬間に少し後ろへ戻ります (1 秒以内)。

**5. 音声を途中から鳴らせない。** シーク・再開・開き直しの後は、次のチャンクの境目まで最大 4 秒無音です。これは API の制限によるもので、README に書いてある仕様です。

### 1.3 案の比較

| 案 | 内容 | 直るもの | 弱み |
|---|---|---|---|
| A. 今のまま、合わせ直しを増やす | `SYNC_INTERVAL` を 20 → 5 tick。`playerSpawn` で書き直す | 3 (遅れが最大 0.2 秒に) | 2 は直らない。送る量が 4 倍 (int 3 個 × 4 回/秒で、小さい) |
| B. サーバーの時計を実時間に | 位置を `Date.now()` の経過で数える。1 tick で足す量は上限 250 ms (ポーズ画面・ワールドの読み込みで止まっていた時間を数えない) | 2 (音声と映像がサーバーで同じ実時間に乗る) | 1 は残る。上限より長い停止 (TPS 4 未満) では遅れる |
| C. クライアントで小さなずれを無視する | Molang で、予測したコマと新しい `frame` の差が N コマ (例 3) 以内なら `base` を変えない | 1 の小さな飛び | ずれが少しずつたまる。N を超えると今と同じく飛ぶ |
| D. 音声をクライアントのアニメーションで鳴らす | リソースパックのアニメーションの `sound_effects` でチャンクを鳴らす | 5 と、音と映像の同期 | アニメーションの時刻と `v.frame` をそろえる仕組みが別に要る。シークの扱いが難しく、実機の確認も無い。大きな作り直し |
| E. サーバーが時刻をプロパティで送る (権威のあるサーバーの時計 + クライアントの補間) | `frame` に加えて、書いた tick の番号 (`tick % 1024` など) を送る | 3 の一部 | クライアントにサーバーの tick を知る手段が無い (Molang に、サーバーと共有する時計が無い)。古さを測れないので、A 以上の効果は無い見込み |

**おすすめ: B + A + (計測しだいで C)。**

- **B** は、根本の 2 を直す唯一の小さな変更です。データ形式・リソースパックを変えません。
- **A** は、`playerSpawn` での書き直しを足すだけで、3 の大半を直します。
- **C** は、B の後もクライアントの小さな飛びが目立つときだけ入れます。Molang を変えるので、変換し直しが要ります。
- **E** (サーバーの時計 + クライアントの補間) は一見正しいですが、Bedrock ではクライアントとサーバーが共有できる時計が無いので、効果がありません。

### 1.4 API の制限

- エンティティのプロパティは int / float / bool / enum だけ。書き込みは次の tick に反映され、1 tick に 1 回まで。
- クライアントの Molang から読めるのは、自分の時計 (`q.life_time`、`q.time_stamp` など) とプロパティだけ。サーバーと共有する時計は無い。
- `playSound` は途中から鳴らせない (開始位置の指定が無い)。止めるのは `stopsound` コマンドだけ。
- `q.life_time` は、エンティティがクライアントで作り直されると 0 に戻る (SPEC.md に記載の前提。変数も消えるので、次の `seq` の変化で合わせ直す)。
- `Date.now()` は 1 ms 単位。シングルプレイでポーズ画面を開くと tick は止まるが、`Date.now()` は進む。

### 1.5 互換のリスク

- 保存する状態 (`<ns>:image_state` の JSON) に `playTicks` がある。B では `playMs` を足し、無ければ `playTicks × 50` から作る。古いワールドの再生位置を保つため。
- `image_main.js` はパックの中にあるので、変えるには変換し直しが要る。古いパックは古い時計のまま動く (壊れない)。
- C は Molang (リソースパック) を変える。B と A は、スクリプトだけで済む。

### 1.6 試験の場面

| 場面 | 作り方 | 見るもの |
|---|---|---|
| 基準 | 何もしない (TPS 20) | 映像と音声のずれ、飛び |
| TPS の低下 | 試験用のビヘイビアーパックで、毎 tick 決まった時間だけ忙しく待つ (TPS 約 10 と約 5) | 同上。サーバーの位置と実時間の差 |
| 複数人 | BDS か LAN で 2 人 | 2 人の映像のずれ |
| 途中で入る | 再生中に 2 人目が入る / スクリーンから離れて戻る | 入った直後の遅れと、飛ぶまでの時間 |
| 一時停止と再開 | 10 秒ごとに 5 回 | 戻る量、再開後の無音の長さ |
| シーク | 前後へ 10 回 | 無音の長さ、コマの正しさ |
| 開き直し | 再生中にワールドを閉じて開く | 続きの位置 |

計り方: 1 コマごとにフレーム番号を焼き込み、1 秒ごとに短い音 (クリック) を入れた試験用の映像を作る。それを OBS で録画し、ffmpeg で録画のコマの番号と音の位置を読み取って、ずれを出す (作業ではゲームを操作して録画するだけ)。

### 1.7 完了の条件

- TPS 約 10 の 60 秒の再生で、映像 (焼き込んだ番号) と音声 (クリック) のずれが常に 0.2 秒以内。音声の途切れがチャンクの境目で 0.3 秒以内。
- TPS 20 で、1 秒ごとの合わせ直しによる飛びが 2 コマ以内。
- 途中で入った人の遅れが 0.25 秒以内 (A の後)。
- 古い版で保存したワールドで、再生位置が保たれる。

### 1.8 足りない自動テスト

クライアントの Molang の式は、生成した文字列をテストしているだけで、時間の進み方は試していない。

- `pre_animation` の式を Python で同じ計算にした「時計の模擬」を作る。サーバーの tick の時間 (ばらつき・遅れ) と、クライアントの時計を別々に進めて、コマの飛びとずれを数えるテストにする。
- 実機の前に、案 B・C の効果を数字で比べられる。

## 2. 人物の切り抜きの ffmpeg の不具合 (音声が映像より短い動画)

### 2.1 ffmpeg の呼び出し方 (`mvcodec/person.py`)

1. **読む側** (`read_frames`): `ffmpeg -i <元> -vf fps=<fps>,scale=... [-t <秒>] -f image2pipe -c:v ppm -`。フィルタは `-vf` の 1 本だけで、`-filter_complex` は使っていない。
2. **人物の範囲の動画** (`_writer`、音声なし): 標準入力の rawvideo → libx264。
3. **背景の動画** (`_writer`、`audio_from=元`):
   ```
   ffmpeg -f rawvideo -pix_fmt rgb24 -s WxH -r FPS -i -  [-t DUR] -i <元>  -map 0:v -map 1:a? -c:a aac  [-shortest]  -c:v libx264 ...
   ```
   - `-shortest` は、長さ (`duration`) を指定しないときだけ付く。
   - コメントによる目的: 音声が映像より長い動画で、音声だけが長く残らないようにする。

### 2.2 実測 (Windows、手元の ffmpeg、10 fps・160×90、切り抜きは常に空のマスクを返す偽物)

| 元の動画 | 結果 | 人物の範囲の動画 | 背景の動画 |
|---|---|---|---|
| 映像 4 秒・音声 1 秒 | `BrokenPipeError` | 映像 1.4 秒 (14 コマ) | 映像 1.0 秒・音声 1.0 秒 |
| 映像 4 秒・音声 1 秒・`duration=4` | 成功 (40 コマ) | 4.0 秒 | 映像 4.0 秒・音声 1.0 秒 |
| 映像 4 秒・音声 6 秒 | 成功 (40 コマ) | 4.0 秒 | 映像 4.0 秒・音声 3.99 秒 (`-shortest` が効いている) |
| 映像 4 秒・音声なし | 成功 (40 コマ) | 4.0 秒 | 映像 4.0 秒 |
| 映像 4 秒・音声 0.1 秒 | `BrokenPipeError` | 0.6 秒 | 映像 0.1 秒 |
| 映像 20 秒・音声 1 秒 | `BrokenPipeError` | 1.4 秒 | 映像 1.0 秒 |

### 2.3 結論 (頼まれた 4 点)

| 問い | 答え |
|---|---|
| `-shortest` が映像を早く終わらせるか | **はい**。背景の動画は、音声の終わり (1.0 秒・0.1 秒) で閉じる |
| フィルタグラフが失敗しているか | **いいえ**。書く側にフィルタは無い。読む側の `Broken pipe` のログは、例外の後に読む側を閉じたときの後片付けのもの |
| 出力の長さが正しくないか | **はい**。失敗する前に書けた分だけの、短い動画が残る |
| 切り抜きそのものが失敗しているか | **いいえ**。切り抜きは動いている。ffmpeg (背景) が標準入力を閉じた後に Python がフレームを書き、`BrokenPipeError` で全体が止まる。人物の範囲の動画も、そこで止まる |

### 2.4 直し方の候補 (手元で試した。最終的には 2.5 の 2 段の方式にした)

`-af apad -shortest` (音声を無音で無限に延ばし、映像の終わりで切る) で、次の 5 つの場合すべてが成功しました。音声の長さは、どれも映像とほぼ同じ (4 秒の映像で 3.99 秒) になりました (実測)。

- 音声が短い・長い・無い・0.1 秒・映像 20 秒 + 音声 1 秒

これは `-shortest` の目的 (長い音声を切る) を保ったまま、短い音声を延ばす形です。音声の無い動画 (`-map 1:a?` が何も選ばない) でもエラーになりませんでした。

`duration` を指定するときの経路 (音声の入力だけを `-t` で切り、`-shortest` を付けない) は、そのまま残します。最後の 1 コマを落とさないための作りだからです。

### 2.5 実装したときに分かったこと (追記)

`-af apad -shortest` を入れると、既存のテスト `test_audio_longer_than_the_video_is_cut_to_the_video_length_without_a_duration` (映像 0.5 秒・音声 3 秒) が落ちました。

- 落ちた理由: 背景の動画の音声が 0.998 秒まで残っていた。
- 映像の長さを 0.1〜2.5 秒で変えて測った結果 (ffmpeg 9.0.1、実測):
  - 映像が 1 秒より短いと、音声が約 1 秒まで残ることがある。同じ条件でも実行ごとに変わる (0.5 秒の映像で、0.49 秒の回と 0.998 秒の回があった)。
  - 映像が 1 秒以上なら、映像の長さちょうどになる。
  - `-max_interleave_delta 0` と `-shortest_buf_duration 0.05` では直らなかった。
- 元の `-shortest` だけの作りにも、もう 1 つ問題があった。音声 1 秒・映像 1.2〜2 秒では、例外にならずに背景の動画が 1 秒で切れていた (パイプの余裕に収まるため)。

採った直し方は、2 段で書く方式です (`mvcodec/person.py` の `_AudioAfterWriter`)。

1. 映像だけを一時ファイルに書き、書いたバイト数からフレームの数を数える。
2. 書き終えた後、`ffmpeg -i <映像だけ> -i <元> -map 0:v -map 1:a? -c:v copy -af apad -c:a aac -t <フレーム数 ÷ fps> <背景>` で音声を足す。

映像 0.1〜20 秒 × 音声 (3 秒・1 秒・0.1 秒・なし・6 秒) の 30 通りで、映像のフレーム数と音声の長さがちょうどになりました (実測)。長さを指定する経路は、1 段のまま変えていません。

### 2.6 テスト

- `make_person_videos` の全体 × 5 つの場合 (音声が短い・長い・なし・0.1 秒・同じ長さ)

  - 人物の範囲と背景の動画を最後までデコードでき、エラーが出ない
  - フレーム数 40・長さ 4 秒 (± 1 フレーム)
  - 音声の長さ 4 秒 (± 0.05 秒)

直す前のコードでは、音声が短い 2 つの場合 (全体と `_writer` で 4 件) が失敗しました。

### 2.7 修正の後の見直し: 終了コードと一時ファイル (追記)

**見つけた問題 (2 段の方式を入れた直後のコード):**

| 問い | 答え |
|---|---|
| ffmpeg の失敗を Python 側で知れるか | `_AudioAfterWriter.wait()` は 0 以外を返していた。ただし `make_person_videos` がその値を捨てていた |
| 不完全なファイルが残るか | 2 段目が失敗すると、本来の名前に途中までのファイルが残りえた |
| 呼び出し側が成功と取り違えるか | 取り違えた (戻り値はフレーム数のまま) |
| stderr を拾えるか | 拾っていなかった (親プロセスの出力に流れるだけ) |

**直したこと (呼び出しの形は変えない):**
- 2 段目は、stderr を拾い、`<名前>.muxing.mp4` に書いて、成功したときだけ `os.replace` で本来の名前にする。
- `make_person_videos` は、書き出しの終了コードが 0 以外なら `InputError` にする。文に stderr を入れる。
- 途中で例外が起きたときは、音声を足さずに一時ファイルだけ消す (`abort`)。
- 標準入力を閉じるときの `BrokenPipe` で、後片付けが止まらないようにする。

**一時ファイルが残るかどうか:**

| 場合 | `*.video-only.mp4` / `*.muxing.mp4` | 確かめ方 |
|---|---|---|
| 正常終了 | 残らない | 自動テスト |
| ffmpeg を起動できない | 作られない | 自動テスト |
| 映像を書いている途中の例外 (切り抜きの失敗) | 残らない。背景の動画も作らない | 自動テスト |
| 2 段目の失敗 | 残らない。背景の動画も作らない | 自動テスト |
| Python のプロセスの強制終了 | **残る**。次に同じ出力を作るときに上書きされ、終わると消える。GUI は一時フォルダの中に作るので、GUI が終わるときに消える | 上書きは自動テスト。強制終了そのものは試していない |

テストは `tests/test_person_audio_length.py` の 24 件 (2.8 で 1 件足した)で、どれも偽の切り抜きを使う。実際の AI のモデルでの確認の手順は、`docs/TESTING.md` の 2.3 (結果は 2.8)。

### 2.8 2 回目の見直しと、実際のモデルでの確認 (追記)

**コードの見直し:**

| 点 | 結果 |
|---|---|
| stderr のデッドロック | 起きない。2 段目は `communicate()` で stderr を最後まで読む。ほかの書き出しの ffmpeg は stderr をパイプにしない。GUI は子プロセスの出力を 1 本のパイプで終わりまで読む |
| `InputError` の分類 | やり直さない扱いは正しい。ただし GUI の知らせの文は「動画を読めませんでした」で、書き込みの失敗には合わない (理由は文の末尾の `{detail}` に出る)。文は直していない |
| 既存のファイルの保護 | 失敗しても、前からあった背景の動画は消さない。**見つけた不具合:** 出来上がったファイルを本来の名前に置き換えられない (Windows で前の動画を別のアプリが開いている) と `PermissionError` のまま上へ伝わり、GUI が「落ちた」と見て、軽い段階で切り抜きをやり直していた。`InputError` にした (テストを 1 件追加。開いたままの実物でも確認) |
| 一時ファイルの名前 | 決まった名前なので、同じ名前の利用者のファイルがあると上書きされて消える (コマンドラインで出力したときだけ。GUI は自分の一時フォルダに書く)。直していない |

**スキップの数が変わる原因:** 手元の Python (Microsoft Store 版 3.13) の Tk が、画面を作るときに自分の `.tcl` のファイルを読めないことがある。GUI のテストは、Tk を作れないときにスキップする。全テストの 3 回のうち 1 回で `tests/test_i18n.py` が 1 件余分にスキップされ、GUI のテスト 3 本を 10 回動かすと 5 回起きた (そのときは 13 件がスキップ)。コードとテストの問題ではない。CI には関係しない。

**実際のモデルでの確認:** `docs/TESTING.md` の 2.3 の表と記録。Python の写真向け・アニメ向けの 10 本と、EXE の 10 本はすべて成功。GUI のだまし絵は、パックの中身まで成功。v6.37.1 では、音声が短い動画が実際のモデルでも失敗する (終了コード 1、背景が 2 秒で切れる)。Minecraft での再生と、CI (Ubuntu) は未確認。

**Linux (Ubuntu) での確認:** この PC には WSL も Docker も無く、WSL を有効にするのは OS の設定の変更なので行っていない。手元にある別の ffmpeg (Playwright 付属の 7.0.1) は libx264 が無く、代わりに使えない。CI で確かめるには、ブランチを push して PR を出す必要がある。

## 3. BDS (専用サーバー) での性能の計り方

### 3.1 計るもの

| 項目 | 計り方 | 今ある道具 |
|---|---|---|
| TPS | 試験用のビヘイビアーパック (別に作る、配布しない) が、`Date.now()` の 5 秒ごとに tick の数を数えてログに出す | ブロックモードの `stats` にも TPS がある。画像モードの `stats` には無い |
| ブロックモードの重さ | `stats` の `stats_play` (fps・TPS・映像の遅れ) と `stats_load` (遅れたフレーム数・1 フレームのスクリプト時間) | あり |
| 画像モードの重さ | TPS の試験用のパック | 画像モードには計測が無い |
| CPU | `Get-Counter '\Process(bedrock_server)\% Processor Time'` を 1 秒ごとに CSV へ | Windows に標準 |
| メモリ | `Get-Counter '\Process(bedrock_server)\Working Set - Private'` (クライアントも同様に `Minecraft.Windows`) | Windows に標準 |
| プレイヤー数 | 1 人と 2 人 (2 人目は別のアカウント・端末が要る) | — |
| 通信量 | クライアントを別の PC か端末にして、サーバーの NIC の `Bytes Sent/sec`。同じ PC だとループバックになり NIC に出ない。代わりは `pktmon` (管理者権限) で UDP 19132 だけ数える | Windows に標準 |
| 1 tick のブロック更新 | 今は数を出していない。モックの見積り (`benchmark/stage_bench.py`、`benchmark/codec_bench.py` の置くブロック数) | 見積りだけ。実測するには `stats` に数を足す (アドオンの変更、TODO.md の P1-1) |

### 3.2 手順 (繰り返せる形)

1. **準備:**
   - BDS (Windows 版、無料) の新しいワールドを作る。スーパーフラット、`allow-cheats=false`、`view-distance=10`。
   - サンプルのアドオン (同じ版の `BlockVideoPlayer-sample-vX.mcaddon` と、画像モードの試験用のパック) を、`worlds/<名前>/behavior_packs`・`resource_packs` に入れて登録する。
   - `server.properties` の `texturepack-required=true`。
2. **基準:**
   - 1 人で入り、スクリーンを置く場所に立ってから 60 秒待つ。
   - TPS・CPU・メモリを記録する。
3. **ブロックモード:**
   - `/badapple:setup` → `/badapple:play <ID>` で最後まで再生する。サンプルの 128×72・10 fps と、重い 256×144。
   - 再生の後に `/badapple:stats`。この間 CPU・メモリ・通信量を 1 秒ごとに記録する。
4. **画像モード:** 同じ場所で、`setup` → `start`。最後まで同じ項目を記録する。
5. **2 人:** 2 人目を入れて 3 と 4 を繰り返す。再生中に入る・抜けるも 1 回ずつ。
6. **回数:** 各場面を 3 回ずつ行い、中央値を取る。同じ場面どうしのばらつきより大きい差だけを効果とみなす。
7. **記録:** docs/PERFORMANCE.md に、BDS の版・PC・アドオンの版と一緒に書く。測れなかった項目は「未計測」と書く。

### 3.3 見込み (実測ではない)

- **画像モードのサーバーの負荷:** プロパティを 1 秒に 3 個書くのと、4 秒ごとの `playSound` だけなので、TPS はほぼ基準のまま (見込み)。
  - 重いのはクライアント (テクスチャのメモリ) と、入るときのリソースパックの送信。パックの大きさは画像モードで数十〜数百 MB。BDS は入るたびに、まだ持っていない人へ送る。
- **ブロックモード:** 実機の Windows の `bench` の値 (`fillBlocks` 1 回 15 µs + 1 ブロック 0.55 µs) から見積もると、128×72 の画面の全部が変わるコマで約 5 ms (見込み)。BDS の CPU は、クライアントと別なので、シングルプレイより余裕がある見込み。
  - ただし、変わったブロックはチャンクの更新として全員に送られるので、人数に比例して通信量が増える見込み。

## 4. GUI と CLI の既定値の違い

### 4.1 違い (コードで確かめた)

| 設定 | CLI (`convert.py` の引数の既定) | GUI (`video_player_gui.py`) / ブラウザ版 (`web/app.js`) |
|---|---|---|
| 幅 × 高さ | 64 × 64 | プリセット「高画質」128 × 128 (縦横比に合わせるボタンで 128 × 72 など) |
| fps | 20 | 10 |
| パレット | `full` (39 色) | `auto` (214 色の候補) |
| ディザ | `none` | `blue_noise` (立体のモードでは `none`) |
| キーフレームの間隔・知覚の最適化・デバイス | 30・あり・auto | 画面の値を渡す (既定は同じ) |
| ほかの全部 (`--block-rdo`・`--temporal-hysteresis`・`--entropy`・`--tile-size`・`--flat-areas` など) | CLI の既定 | GUI は渡さないので CLI の既定 |

### 4.2 違う理由 (コードと履歴から)

- CLI の既定は、初期 (v1〜v4) の値のまま残っている。GUI は、自動パレット (v6.10)・Blue Noise (v6.14) を入れるたびに、画面の既定だけを変えた。
- CLI の既定を変えなかったのは、出力が変わるため。CLI の既定の出力に頼っているのは次のもの。
  - ベンチマーク (`benchmark/run.py`、`benchmark/real_video_bench.py` が前のタグと比べる週 1 回の CI)
  - テスト
  - 使う人のスクリプト
- プリセットは、GUI (Python の `QUALITY_PRESETS`) とブラウザ版 (JS の `QUALITY_PRESETS`) に 2 回書いてあり、`tests/test_web_parity.py` が一致を確かめている。

### 4.3 共通の定義を入れる案 (互換を保つ)

1. `conversion_profiles.py` (データだけ) に、`recommended` (今の GUI の既定) と `legacy` (今の CLI の既定) を置く。プリセットの表もここへ移す。
2. GUI はここから既定を読む。ブラウザ版は、`scripts/build_web.py` がここから JSON を書き出して読む。
   - Pyodide でも、同じ Python を import できる。
3. CLI に `--profile recommended|legacy` を足す。**既定は `legacy` のまま** (今の出力を 1 バイトも変えない)。
   - 個別の引数は、プロファイルより優先する。
   - 既定を `recommended` に変えるかは、次の大きな版で、CHANGELOG と DECISIONS.md に書いてから決める。
4. はじめてガイドと、TODO.md の P1-6 (モードの勧め) も同じ表を使う。

### 4.4 確かめるテスト

- GUI の `build_converter_args(既定)` の引数と、`convert.py --profile recommended` が解釈した引数 (argparse の Namespace) が、全項目で一致する。
- 同じ短い映像を、GUI の引数と `--profile recommended` で変換すると、出力 (.js) がバイト単位で一致する。`--threads 1` で、乱数の種は同じにする。
- `--profile legacy` と、引数なしの出力が一致する (今の動きを壊していない)。
- ブラウザ版の書き出した JSON と、`conversion_profiles.py` が一致する (`test_web_parity.py` の置き換え)。

## 6. 結論: 実装の順番

| 順 | 作業 | 理由 |
|---|---|---|
| 1 | 切り抜きの音声の不具合を直す (`-af apad -shortest`) | 原因と直し方が実測で確かめられ、再現テストもある。小さく、使う人の失敗を直接減らす |
| 2 | ドキュメントのずれを CI で見つける (TODO P0-1) | 小さく、以後のリリースのたびに効く |
| 3 | 画像モードの時計: 実機で計る → 案 B + A | 根本の原因の推測 (TPS で音声が途切れる) を、まず計って確かめる。直すのはスクリプトだけで済み、データ形式を変えない |
| 4 | 時計の模擬のテスト (1.8) | 3 の効果を、実機の前に数字で比べられる。今後の時計の変更の回帰も防ぐ |
| 5 | BDS の計測 (3 章の手順) | 無料で手元でできる。画像モードの TPS の計測には、3 と同じ試験用のパックを使う |
| 6 | 共通の設定の定義 (4.3) | 出力を変えずに入れられる。AI エージェントと人が CLI で戸惑うのを防ぐ。急ぎではない |
